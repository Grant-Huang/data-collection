## 三、生成的两个DAG详细描述

### DAG-1: 连续尺寸超差异常处理

```
开始 "发现尺寸超差"
  ↓
活动 "暂停设备并隔离产品" (操作员)
  ↓
活动 "质量工程师复测" (质量工程师)
  ↓
决策 "是否确认超差？"
  ├─ 是 → 并行分析
  │    ├─ 活动 "设备侧检查" (设备工程师)
  │    └─ 活动 "工艺/刀具侧检查" (工艺工程师)
  │        ↓
  │    活动 "汇总分析结果"
  │        ↓
  │    活动 "试产并首件检验" (操作员、质量工程师)
  │        ├─ 合格 → 恢复生产 (结束)
  │        └─ 不合格 → 重新进入"并行分析"阶段(重试)
  │
  └─ 否 → 恢复生产 (结束)
```

**关键特征**:
- ✅ 包含并行处理块（两条检查线同时进行）
- ✅ 包含重试循环（首件不合格时重新分析）
- ✅ 4个参与角色（涉及跨团队协作）
- ✅ 2个决策点（两处业务分岔）

**嵌入的规则与经验**:
1. 连续3件超差必须立即通知质量工程师
2. 超差原因的并行分析能大幅缩短诊断时间
3. 异常扩大时操作员应先停机等待，不盲目调试
4. 设备和工艺的并行检查是最佳实践

---

### DAG-2: 伺服系统故障排查与维修

```
开始 "设备故障报警"
  ↓
活动 "检查故障代码和日志" (设备工程师)
  ↓
决策 "是否为过热保护？"
  ├─ 是
  │  ├─ 活动 "清理散热、检查风扇"
  │  └─ 活动 "机器冷却并重启"
  │      ↓
  │      决策 "重启是否成功？"
  │      ├─ 是 → 交付生产 (结束)
  │      └─ 否 → 进入硬件诊断
  │
  └─ 否 → 活动 "硬件诊断测试" (示波器检查等)
           ↓
           决策 "是否有硬件故障？"
           ├─ 是 → 活动 "更换故障零件"
           │       ↓
           │       活动 "系统调试和验证"
           │       ↓
           │       决策 "运动验证是否通过？"
           │       ├─ 是 → 负荷测试 → 交付生产 (结束)
           │       └─ 否 → 回到硬件诊断(重试)
           │
           └─ 否 → 交付生产 (结束)
```

**关键特征**:
- ✅ 完整的决策树结构（4个决策点）
- ✅ 逻辑的串行流转（"修复→调试→验证→负荷测试"）
- ✅ 多个重试路径（验证不通过回到诊断）
- ✅ 清晰的故障诊断层级（过热→硬件→修复→验证）

**嵌入的规则与经验**:
1. 故障诊断必须从代码/日志开始，避免盲目拆卸
2. 过热保护通常是风扇或通风问题，优先检查
3. 硬件故障必须用专业工具（示波器）诊断
4. 零件更换后必须进行运动验证和负荷测试
