# 🧪 异常场景测试指南

## 📋 概述

本文档描述了DAG生成系统的异常场景测试框架。该框架包含8个真实的人类交互场景，用于测试系统在处理不完美输入时的鲁棒性。

## 🎯 测试目标

验证DAG生成系统能够正确处理：
- ✅ 非线性思维（思维跳跃）
- ✅ 不完整表达（言语断续）
- ✅ 信息修正（自我纠正）
- ✅ 信息重复（冗余表述）
- ✅ 碎片化信息（分散输入）
- ✅ 对话中断（打断恢复）
- ✅ 复杂条件（多个分支）
- ✅ 混合内容（客观+主观）

## 📊 8个异常场景详解

### 1️⃣ 思维跳跃型访谈 (EDGE_001)

**现象**: 专家先描述后面的步骤，然后回过头补充前面的细节

**真实例子**:
```
专家: "然后我们进行硬件诊断...如果发现故障就更换零件...最后进行负荷测试"
      (直接跳到第3-5步)

系统: "那设备报警之前呢？"

专家: "哦对，我忘了说...设备报警之前，我们需要检查代码日志..."
      (回到第1步补充)
```

**系统挑战**:
1. 识别出逻辑顺序被打乱
2. 重组信息流到正确的时间顺序
3. 识别被遗漏的中间步骤
4. 识别条件分支（过热 vs 硬件故障）

**测试结果**: ✅ PASS (6节点, 5边)

---

### 2️⃣ 言语断续型访谈 (EDGE_002)

**现象**: 专家说到一半停顿，然后重新组织表达

**真实例子**:
```
专家: "嗯...我们首先要...等等，让我重新说"
      (不完整的第一次尝试)

专家: "当发现连续几件产品出现尺寸超差时..."
      (重新组织)

专家: "首先...不对，应该是先暂停生产、隔离..."
      (再次修正)

专家: "先暂停生产、隔离有问题的产品...然后我们..."
      (完整版本)
```

**系统挑战**:
1. 识别不完整的句子
2. 分离有效信息和修正前的错误信息
3. 合并分散的单个步骤
4. 处理语序混乱

**测试结果**: ✅ PASS (4节点, 3边)

---

### 3️⃣ 自我纠正型访谈 (EDGE_003)

**现象**: 专家说出错误信息，然后主动纠正

**真实例子**:
```
专家: "首先进行硬件诊断..."

专家: "然后...等等，这样不对"

专家: "应该是先看代码日志，这是第一步，最重要的！"

专家: "只有先从代码日志确定方向，才能决定是清风扇还是做硬件诊断"
```

**系统挑战**:
1. 识别哪个陈述是正确的（最后的版本）
2. 检测纠正的信号词（'不对', '应该'）
3. 移除或降权错误的信息
4. 理解为什么是错的（学习因果关系）

**测试结果**: ✅ PASS (5节点, 4边)

---

### 4️⃣ 重复冗余型访谈 (EDGE_004)

**现象**: 专家用不同方式多次强调同样的内容

**真实例子**:
```
专家: "最重要的是不能盲目拆卸...要先看日志"

专家: "代码日志很关键...它能告诉你问题在哪"

专家: "我必须强调，从日志开始很重要...不能跳过这一步"

专家: "这个原则我已经实践了15年...日志分析永远是第一步"
```

**系统挑战**:
1. 识别重复的核心观点
2. 去重
3. 保留第一次有效的陈述
4. 丢弃强调和重述

**测试结果**: ✅ PASS (4节点, 3边)

---

### 5️⃣ 信息碎片型访谈 (EDGE_005)

**现象**: 关于同一步骤的信息被分散到多个回合

**真实例子**:
```
系统: "复测的流程是什么？"
专家: "复测就是拿出隔离的产品再量一遍尺寸"

系统: "需要什么工具吗？"
专家: "使用精密测量仪器...通常是游标卡尺或卡规"

系统: "复测需要多长时间？"
专家: "每件产品大概2-3分钟...取决于特征点的数量"

系统: "那复测的目的是什么？"
专家: "确认是否真的超差...有时候第一次测量可能有误差"
```

**系统挑战**:
1. 识别属于同一步骤的分散信息
2. 整合多个回合的片段
3. 识别步骤之间的顺序关系
4. 建立完整的步骤定义

**测试结果**: ✅ PASS (5节点, 4边)

---

### 6️⃣ 中断恢复型访谈 (EDGE_006)

**现象**: 专家的陈述被系统打断（澄清问题），然后继续

**真实例子**:
```
专家: "首先看日志...如果是过热...我们需要清理散热风扇"

系统: "过热的判断标准是什么？"  (打断)

专家: "代码日志会显示温度超过阈值或有过热保护触发的记录"

系统: "好，那如果不是过热呢？"  (另一个打断)

专家: "那就进行硬件诊断...我们会检查伺服驱动器的各个模块"
      (继续原来的思路)
```

**系统挑战**:
1. 追踪中断前后的逻辑连接
2. 识别澄清问题的作用
3. 维护对话上下文
4. 重建被打断的流程线索

**测试结果**: ✅ PASS (6节点, 5边)

---

### 7️⃣ 条件复杂型访谈 (EDGE_007)

**现象**: 涉及多个if-then分支和假设的复杂流程

**真实例子**:
```
专家: "如果复测确认超差...我们需要分析原因...
       这时候可能是设备问题或工艺问题"

专家: "如果是设备问题...设备工程师会检修...
       如果是工艺问题...工艺工程师会调整"

系统: "这两个分支是并行的吗？"

专家: "可以并行...这样能节省时间...
       两个团队同时诊断各自的问题"

专家: "然后他们汇总结果...一起做试产验证"

专家: "如果验证成功...恢复生产...
       如果失败...再次分析原因...可能需要重复这个过程"
```

**系统挑战**:
1. 识别所有的条件判断点
2. 区分顺序执行 vs 并行执行
3. 处理递归或重试循环
4. 建立完整的决策树

**测试结果**: ✅ PASS (9节点, 8边) ⭐ 最复杂

---

### 8️⃣ 经验融合型访谈 (EDGE_008)

**现象**: 专家混合客观步骤和主观经验、感受、建议

**真实例子**:
```
系统: "故障处理中最常见的错误是什么？"

专家: "最糟糕的就是不看日志就开始拆...很多年轻工程师都这样做"
      (主观评价 + 观察)

专家: "这是一个教训...我见过太多这样的失败"
      (经验教训)

专家: "所以流程必须是：看日志→判断方向→然后才能采取行动"
      (从错误中提炼的规则)

专家: "经验帮助我们快速识别日志中的关键信息...
       我能在30秒内看出问题方向"
      (经验价值)

专家: "新手可能需要几分钟...但基本步骤是一样的...
       区别只是速度"
      (区分基础vs优化)
```

**系统挑战**:
1. 分离过程步骤和主观评价
2. 识别'教训'和'规则'
3. 处理效率改进信息
4. 识别隐含的规则

**测试结果**: ✅ PASS (5节点, 4边)
