# Phase 3-A LLM 采集提示词优化指南

本文档说明如何优化 LLM 采集流程提示词，以支持 Phase 3-A 的新维度。

## 概述

Phase 3-A 引入了 4 个新的复杂维度，需要在采集提示词中添加相应的问题和引导，帮助 LLM 从专家的自然语言表述中提取结构化的信息。

**核心原则**：
- 用自然语言问题，而非要求填写 JSON 字段
- 根据答案自动将其转换为 Schema 结构
- 提供具体的例子和对比，帮助 LLM 理解

---

## 采集阶段划分

现有的采集流程通常分为 6 个主要阶段（P1-P6），我们在以下阶段添加新问题：

| 阶段 | 现有内容 | Phase 3-A 新增 |
|---|---|---|
| P1 | 场景背景、触发器 | 无变化 |
| P2 | 节点清单、关键操作 | 无变化 |
| P3 | 节点详情（角色、描述等） | 无变化 |
| P4 | 边和流程逻辑 | 无变化 |
| P5 | 时间约束、决策条件 | 增加聚合条件问题 ❌ → 📊 |
| P6 | 评估规则、异常处理 | **新增 5 类问题** |

## P6 阶段的新增问题

### 问题集 1: 权限分级和多层签字

**适用节点**：Decision、Approval 等涉及批准的节点

**问题列表**：

```markdown
### 👥 权限和批准流程

在这个决策/批准节点：

1. **是否需要多个角色的批准？**
   - 示例：是，需要工艺、质量、设备三个工程师都批准
   - 示例：否，只需要设备工程师批准
   
2. **如果需要，这些批准是顺序进行还是可以并行？**
   - 顺序示例：先工艺工程师检查参数，再质量工程师检查首件，最后设备工程师批准
   - 并行示例：工艺和质量可以同时检查，都通过后再由设备工程师批准

3. **每个角色的具体评估标准是什么？**
   - 工艺工程师：[具体标准，如"工艺参数在范围内，刀具寿命充足"]
   - 质量工程师：[具体标准]
   - 设备工程师：[具体标准]

4. **如果某个角色拒绝了这个批准，会怎样处理？**
   - 示例：升级到生产主管重新评审
   - 示例：停止流程，通知所有相关人员
```

**LLM 处理逻辑**：

```python
def extract_approval_matrix(response_text):
    """
    从自然语言响应中提取权限矩阵
    
    返回：
    {
        "has_approval_matrix": True/False,
        "roles": [list of roles],
        "sequence": "parallel" or "sequential",
        "criteria": {role: criteria_text},
        "escalation": escalation_text
    }
    """
    # LLM 分析响应文本，识别关键概念
    # - 多个角色 → has_approval_matrix = True
    # - "同时"/"并行" → sequence = "parallel"
    # - "先...后..." → sequence = "sequential"
    # - 每个角色的条件 → criteria
    # - "升级到..." → escalation
```

### 问题集 2: 聚合条件和趋势判断

**适用节点**：Decision 等涉及条件判断的节点

**问题列表**：

```markdown
### 📊 条件判断的聚合方式

在进行"[决策问题]"时：

1. **决策条件是基于单个测量点，还是需要看历史趋势？**
   - 单点示例：设备温度 > 50°C 就要停止
   - 趋势示例：设备温度持续上升（连续 3 次上升超过 2°C）才需要停止
   - 模式示例：缺陷在特定位置连续出现（连续 2 个产品同位置缺陷）

2. **如果是趋势判断，需要看多少个历史数据点？**
   - 示例：过去 7 个产品或 7 个测量点
   - 示例：最近的 5 次测试结果
   
3. **趋势的具体判断规则是什么？**
   - 上升趋势：所有点都在上升，每次上升 > [阈值]
   - 下降趋势：所有点都在下降
   - 连续超差：连续 N 个点超过上限
   - 周期模式：每隔一段时间重复出现问题

4. **在做这个判断之前，至少需要积累多少数据点？**
   - 示例：至少 3 个点，否则数据太少无法判断
   - 示例：至少 5 个点
```

**LLM 处理逻辑**：

```python
def extract_aggregation_condition(response_text):
    """
    从自然语言响应中提取聚合条件
    
    返回：
    {
        "has_aggregation": True/False,
        "method": "trend|pattern|continuous|statistical",
        "window_size": int,
        "operator": "all_increasing|all_decreasing|two_exceeding|...",
        "threshold": threshold_value,
        "min_samples": int,
        "description": natural_language_description
    }
    """
    # LLM 分析响应文本
    # - "持续上升"/"趋势" → method = "trend", operator = "all_increasing"
    # - "连续 N 个" → method = "pattern"
    # - 数字 7 或"七个" → window_size = 7
    # - 数字 3 → min_samples = 3
```

### 问题集 3: 临时措施和有效期限制

**适用节点**：Activity、Decision 等涉及异常处理的节点

**问题列表**：

```markdown
### ⏳ 临时措施和有效期

在进行"[操作/决策]"时：

1. **这是一个临时措施吗？（如临时 bypass、临时参数调整）**
   - 示例：是的，这是设备故障期间的临时 bypass，等设备修好就不用了
   - 示例：否，这是常规流程

2. **如果这是临时措施，它的有效期是多长？**
   - 时间限制示例：72 小时
   - 产品数量限制示例：3 个 lot（批次）
   - 组合限制示例：72 小时 OR 3 个 lot，先达到任一条件就失效
   
3. **有没有特殊的失效条件？**
   - 示例：如果 30 天内同一问题再次出现，立即失效并启动正式改进（CAPA）
   - 示例：如果需要连续使用超过 3 次，就必须替换为正式解决方案
   
4. **如果这个临时措施被多次使用，应该怎样处理？**
   - 示例：第二次使用就要升级到管理层审批
   - 示例：重复使用 3 次后启动 CAPA 流程
   - 示例：不设置升级，允许反复使用（但有时间/次数限制）
```

**LLM 处理逻辑**：

```python
def extract_temporary_measure(response_text):
    """
    从自然语言响应中提取临时措施信息
    
    返回：
    {
        "is_temporary": True/False,
        "expiration": {
            "duration": "PT72H" or natural_language,
            "lot_count": int,
            "trigger": "duration_or_count|duration_and_count"
        },
        "revocation": {
            "type": "time_passed|reoccurrence|condition_met",
            "days": int,
            "description": natural_language_description
        },
        "escalation_on_repeat": {
            "enabled": True/False,
            "trigger": "same_condition|pattern_detected",
            "action": "escalate_to_manager|create_capa|..."
        }
    }
    """
    # LLM 分析响应文本
    # - "临时"/"设备故障期间" → is_temporary = True
    # - "72 小时" → duration = "PT72H"
    # - "3 个 lot" → lot_count = 3
    # - "30 天内再出现" → revocation.type = "reoccurrence", days = 30
    # - "升级"/"CAPA" → escalation_on_repeat.enabled = True
```

### 问题集 4: 多维追溯和隔离范围

**适用节点**：Activity、Event 等涉及异常处理的节点

**问题列表**：

```markdown
### 📍 问题的追溯范围和产品隔离

当发现"[问题类型]"时：

1. **会影响哪些产品？追溯范围是什么？**
   - 设备隔离示例：此设备加工的所有产品都要隔离
   - 物料批次示例：仅隔离使用同一批物料的产品
   - 组合示例：同一班次内使用同一物料的产品
   
2. **不同的根因会导致不同的隔离范围吗？**
   - 示例 1：如果是设备问题，隔离此设备上的所有产品
   - 示例 2：如果是物料问题，仅隔离同批物料的产品
   - 示例 3：如果是工艺参数问题，隔离此班次的产品
   
3. **隔离产品需要什么处理？**
   - 示例：100% 复测
   - 示例：客户通知
   - 示例：退货处理

4. **追溯信息的记录和跟踪方式**
   - 示例：记录隔离的精确时间和产品编号
```

**LLM 处理逻辑**：

```python
def extract_containment_scope(response_text):
    """
    从自然语言响应中提取隔离范围
    
    返回：
    {
        "dimension": "equipment_id|lot_id|material_id|line_id|...",
        "rule": descriptive_rule_text,
        "affected_product_estimate": int or "unknown",
        "conditions": [list of conditions when this rule applies],
        "description": natural_language_description
    }
    """
    # LLM 分析响应文本
    # - "此设备" → dimension = "equipment_id"
    # - "同一批物料" → dimension = "material_id"
    # - "同班次" → dimension = "shift_id"
    # - 具体隔离规则 → rule
    # - 影响范围 → affected_product_estimate
```

### 问题集 5: 异常处理的其他维度（补充）

**适用节点**：所有异常处理相关的节点

**问题列表**：

```markdown
### 🔧 异常处理的额外信息

1. **当这个异常被处理后，有什么事后跟踪吗？**
   - 示例：需要 Engineering Change Notice (ECN)
   - 示例：需要长期监测该参数

2. **这个异常处理流程与其他工作流有交互吗？**
   - 示例：需要通知采购部门（供应链工作流）
   - 示例：需要上报管理层（汇总报告工作流）

3. **有没有已知的替代解决方案？**
   - 示例：方案 A（快速但临时），方案 B（费时但永久）
```

## 现有采集问题的调整

### P5 阶段的调整

**原问题**：这个决策/判断点的条件是什么？

**调整后**：
```markdown
这个决策/判断点的条件是什么？

- 是单个指标的阈值判断？
  示例：温度 > 50°C
  
- 还是需要结合多个条件？
  示例：温度 > 50°C AND 湿度 > 80%
  
- 还是需要看趋势/历史数据？
  示例：温度持续上升（见下面的详细问题）
  
[如果是趋势，跳转到问题集 2]
```

## 采集工作流示例

### 场景：设备温度异常处理

**采集对话示例**：

```
LLM: "在温度检查这个决策点，条件是什么？"

专家: "我们会监控设备的实时温度。通常 50°C 以下没问题，
      但我们注意到，即使温度没有超过 50°C，如果它一直在上升，
      通常在 1-2 小时后就会超过 60°C，所以我们设置了一个趋势告警。"

LLM: [自动识别聚合条件] 
     "所以这是一个趋势判断？看最近多少个测量点？"

专家: "我们每 5 分钟测一次，看最近 7 个点（约 35 分钟）。
      如果 7 个点都在上升，且平均每次上升 2°C 以上，就要采取行动。"

LLM: [自动提取] 
     "明白了。那发现这个趋势后的处理是什么？需要多角色批准吗？"

专家: "首先要通知设备工程师，他要检查油路和冷却系统。
      同时通知工艺工程师，可能需要调整参数来降低发热。
      如果两个都说没问题，才能继续生产。"

LLM: [识别权限矩阵] 
     "是并行检查还是顺序检查？"

专家: "可以并行。设备工程师和工艺工程师同时检查，都确认没问题就行。
      但如果其中一个说有问题，就要升级到生产主管决定是停机还是调试。"

LLM: [完整记录]
     "这个对话中有几个临时措施吗？比如说，在等待修复期间有什么临时办法？"

专家: "有。如果是油路堵塞临时无法完全修复，可能会临时降低生产速度
      来减少发热。这个措施最多用 3 天，或者 10 个 lot，先到为准。
      如果 3 个月内同样问题再出现，就必须做根本改造。"

LLM: [识别临时措施]
     "好的，我已经完整记录了。这个流程中还有其他内容吗？"
```

## LLM 提示词模板

### 模板结构

```markdown
# Phase 3-A 采集流程 - P6 阶段完整提示词

## 背景
当前采集工作流：[workflow name]
当前节点：[node name]

## 任务
从专家描述中提取以下信息，并转换为结构化数据：
1. 权限分级和多层签字（如适用）
2. 聚合条件和趋势判断（如适用）
3. 临时措施和有效期（如适用）
4. 多维追溯和隔离范围（如适用）

## 问题序列

### 第一轮：快速筛查
- "在这个[节点类型]中，需要多角色批准吗？"
- "条件判断是单点还是需要看趋势？"
- "有没有临时措施或应急方案？"
- "如果发现问题，会隔离哪些产品？"

### 第二轮：深入了解（根据第一轮答案）
[跳转到相应的问题集]

### 第三轮：验证和澄清
- 总结提取的信息
- 询问是否有遗漏

    "temporary_measure": {...},
    "containment": {...},
    "notes": "..."
}
```

## 实现步骤

1. **更新采集提示词库**（1-2h）
   - 添加新的问题集到现有的采集系统
   - 更新 P6 阶段的流程逻辑

2. **LLM 抽取逻辑开发**（2-3h）
   - 为每个新维度编写抽取函数
   - 测试自然语言理解准确率

3. **采集样本验证**（1-2h）
   - 用 1-2 个真实工作流测试新采集流程
   - 调整问题措辞和抽取逻辑

4. **采集工程师培训**（0.5h）
   - 解释新维度的含义
   - 示范采集过程

**总工作量**：4.5-7.5 小时

---

## 质量检查清单

采集完成后，检查以下项目：

- [ ] 权限矩阵中的所有角色都能识别
- [ ] 聚合条件的 window_size 和 operator 合理
- [ ] 临时措施有明确的有效期和失效条件
- [ ] 隔离范围的维度在允许列表中
- [ ] 所有提取的数据都通过 Validator 检查
- [ ] 采集专家确认没有遗漏关键信息
