## 1. 背景与目标

### 1.1 要解决的问题

现有的制造专家知识主要停留在专家脑子里，缺少结构化、可追溯、可用于 AI 训练/实验的采集方式。人工画流程图（BPMN/DAG）对制造专家有极高的学习门槛，因此产品的核心主张是：

> **专家只需要像聊天一样，讲自己真实做过的一件工作；系统负责把自然语言实时整理成结构化的工作流图（Graph），专家只需要确认和纠错，不需要学习任何建模术语。**

### 1.2 目标用户

MES/车间管理、质量、设备、工艺、计划、IE、精益生产等制造专家。采集入口面向专家本人，管理/研究侧（数据集、Dashboard、实验中心）面向产品经理、算法与数据工程角色，不在本次移动端改造范围内。

### 1.3 本次 PRD 的范围

- **In scope**：专家会话式采集的桌面端产品需求盘点（已有设计的结构化整理） + 移动浏览器端新增体验设计（会话主页、语音输入、DAG 只读查看）。
- **Out of scope（沿用现状，不在本次重新设计）**：数据集管理、Dashboard、实验中心——这三块已有独立的设计文档（`design/dataset_design_spec.md`、`design/manufacturing_workflow_platform_design_v2.md` 第16~31节），本次不改动，仅在第7节指出它们与采集层共享同一套 Schema 时需要注意的口径问题。
- **不做**：
  - 移动端 DAG 图的编辑能力（本次评审已确认，见 2.2）
  - **移动端不提供实验中心入口**：手机浏览器端只服务"专家数据采集"这一件事（会话页 + 历史抽屉 + DAG只读页），不做数据集管理、Dashboard、实验中心的移动适配，这三块继续保持桌面专属（详见 4.6）
  - **不接入公网/互联网搜索**：本产品是**封闭域**的数据采集与实验平台，专家讲述的是自己真实经历的工作，AI 引导模型也只基于会话上下文做澄清追问，不联网检索资料、不做事实核查、不引用外部网页。这一条**是对 `docs/app-design.md`（本仓库既有的 VoiceChat/web-demo 语音产品设计）里规划中的"过渡语 + 未来接入新闻搜索等外部工具调用"能力的明确排除**——那是另一个产品（VoiceChat 日常语音助手）的规划方向，本产品不继承（详见 4.7）

## 2. 移动端需求：已确认的产品决策

这三条是本次讨论中明确拍板的，作为后续所有移动端设计的前提，不再反复讨论：

### 2.1 语音回复形式：文字为主

移动端「实时语音会话」中，专家可以语音说话，但 **AI 的回复以文字气泡呈现，不做语音播报（TTS）**。语音只是一种输入方式，采集节奏和桌面端的追问逻辑完全一致。

- 不引入 TTS、打断、回声消除等语音播报相关机制，大幅降低移动端实现成本
- 更适合车间等嘈杂环境下的实际使用场景（专家不方便一直听语音回复）
- 与本仓库 `web-demo` 里已经验证过的"实时语音全双工对话"（VoiceChat 模式）是**两回事**，本产品移动端复用的是 `web-demo` 中"语音识别转写"这一段能力（Realtime 协议的 `input_audio_transcription`），不复用其语音播放/打断/回声消除那一整套机制

### 2.2 移动端 DAG 页面：完全只读

右滑看到的 DAG 页面在移动端**只用于查看和确认，不支持编辑**。所有纠错（改节点文字、改分支条件、标记"这里不对"等）都必须回到会话页面，用自然语言说出来，由 AI 转成 Graph Ops 后由后端校验生效。

- 移动端不需要实现拖拽节点、点击编辑表单等触控交互，只需要实现"缩放 + 平移 + 点节点看详情（只读弹层）"
- 这与桌面端设计（`design/conversational_collection_design.md` 第22节、`design/manufacturing_workflow_platform_design_v2.md` 第10.2节）形成明确分工：**桌面端保留完整的点图纠错能力，移动端纠错入口收敛回会话**

### 2.3 右滑手势：非边缘区域触发

主屏幕（会话页）向右滑动切换到 DAG 页面，**判定区域必须排除屏幕左边缘约 20px 的系统手势保留区**，避免与 iOS Safari / 主流移动浏览器"从屏幕边缘右滑 = 返回上一页"的系统手势冲突。

- 具体交互规范见第 5.4 节

## 3. 现状盘点：桌面端设计（已有，本次整理归档）

以下内容来自 `design/conversational_collection_design.md`（v2.1，DAG-first）与 `design/manufacturing_workflow_platform_design_v2.md`（更早版本的完整平台说明书），两者对采集层的设计基本一致，本节做统一整理，作为移动端设计的对照基准。桌面端本次**不做改动**。

### 3.1 页面结构

固定竖向三栏（桌面宽度 ≥ 1180px 体验最佳）：

| 分栏 | 内容 | 建议宽度 |
|---|---|---|
| 左栏 | 历史流程清单（专家过去回答过的所有流程，可继续/复制/搜索/筛选） | 240–280px |
| 主栏 | 会话式采集（AI ↔ 专家，自然语言输入） | 自适应，占最大空间 |
| 右栏 | 实时 DAG 图 + 结构化摘要 + 规则/经验 + 待确认项 | 400–460px |

### 3.2 采集原则

1. **不问术语，只问业务**：不出现"分支""并行""汇合""DAG""Loop Back"这些词，全部转成自然语言问句（例如"这两件事是先后做，还是可以同时做？"）
2. **7B 引导模型的职责边界**：只负责引导、复述、澄清、结构化抽取、选择下一条最有价值的追问；**不允许**猜测未说出的事实、自动补 SOP、编造角色/阈值、为了图完整而创造节点/边、静默解决冲突
3. **不是固定 Wizard**：内部分 8 个采集阶段（触发发现→主干发现→分支发现→并行汇合发现→角色系统发现→规则经验发现→结束条件发现→专家复核），但专家提前说出后面信息时立即提取，不强制按顺序问
4. **每轮只问一个最重要的问题**（优先级 P0 主干 → P1 分支 → P2 并行 → P3 汇合 → P4 审批/交接 → P5 返工重试 → P6 规则经验 → P7 研究增强）

### 3.3 DAG 数据模型要点

- 节点类型：`start / activity / decision / parallel_split / parallel_join / merge / approval / handoff / wait / end`（后续可扩展 `event / subprocess`）
- 边类型：`normal / conditional / parallel / merge / handoff / approval / timeout / exception_forward`
- **返工/重试不建边**，而是作为节点的 `retry_semantics` 语义附加信息保存，保证主图始终是合法 DAG，可稳定拓扑排序（这是 v2.1 版本相对更早版本的关键升级，详见第 7 节的口径冲突说明）
- 每个节点/边必须保留 `source_turn_ids`（证据可追溯）、`confidence`、`expert_confirmed`——模型抽取结果不等于已确认事实

### 3.4 冲突处理

前后表述矛盾时（例如"质量主管批准"vs"班组长决定"），系统不得静默覆盖，必须生成 `conflicts` 并追问澄清。

### 3.5 完成度与提交

- Completion Score 按 9 个维度加权（Trigger 10% / 主干 20% / 分支条件 15% / 并行汇合 15% / 角色交接 10% / 系统证据 5% / 规则经验 10% / 结束条件 10% / 专家确认 5%），流程本身没有分支/并行时权重重新分配到主干和结束条件，不扣分
- `>= 80` 进入最终确认；最终确认页面停止主动追问，专家看完整 DAG 后点"确认并提交"或"继续修改"
- 提交后保存四份数据：原始转写、DAG图JSON、归一化图JSON、会话抽取轨迹；已提交流程再次修改生成新版本，不覆盖旧版本

## 4. 新增需求：移动浏览器端体验设计

### 4.1 设计原则

移动端不是桌面三栏的简单压缩，而是围绕"专家最可能在车间/产线现场、边走边说"这个使用场景重新设计交互，同时最大程度复用本仓库 `web-demo/`（VoiceChat 语音对话产品）已经验证过的移动端语音交互范式（胶囊输入栏、语音波形状态、口述转文字三按钮），不重新发明一套语音 UI。

### 4.2 页面结构：两页 + 一个抽屉

```
┌─────────────────────────┐        ┌─────────────────────────┐
│  ☰  CNC尺寸超差处理   ⓘ │  右滑→ │  ←  当前整理出的流程     │
│                          │  ←左滑 │                          │
│      会话页（主页）      │        │      DAG 只读查看页      │
│   AI ↔ 专家对话气泡      │        │   可缩放 / 可平移        │
│                          │        │   点节点看详情           │
│  [胶囊输入栏 + 麦克风]   │        │   底部：结构摘要/待确认  │
└─────────────────────────┘        └─────────────────────────┘
        ↑ 点击左上角 ☰
┌─────────────────────────┐
│  我的流程          ✕    │
│  ─────────────────────  │
│  CNC尺寸超差处理  67%    │  （对应桌面端左栏）
│  夜班缺料补料流程 已确认  │
│  换型首件确认      35%   │
│  + 新建一个流程          │
└─────────────────────────┘
```

- **会话页 = 移动端默认主页**（对应桌面端主栏），这是这次改动里最关键的一条：移动端不是"三栏挤成一栏后第一屏是历史列表"，而是**直接进入当前会话**，历史列表退居为左上角抽屉，与桌面端"专家一进来就该继续/开始讲述"的产品心智保持一致
- **左上角列表图标（☰）**：点开后从左侧滑出历史流程抽屉（对应桌面左栏的全部功能：搜索、状态筛选、场景筛选、新建流程、复制变体、删除草稿），覆盖在会话页之上，点击遮罩或流程项关闭抽屉
- **主页右滑 → DAG 页**：对应桌面右栏，只读查看（见 2.2、5.4）
- 顶部栏右侧的 ⓘ / `···` 可以放"检查流程完整度"入口（对应桌面右栏顶部"检查流程"按钮），不做成常驻面板，避免挤占会话区域

### 4.3 会话页设计（借鉴 web-demo 的语音交互范式）

移动端会话页的视觉与交互方向直接复用 `docs/app-design.md` 第一节已经验证过的"ChatGPT App 风格"设计语言，而不是重新设计一套：

- 极简顶栏：左侧列表图标 + 中间流程名（或"新的流程"）+ 右侧辅助入口，无大标题栏
- 对话区：AI 气泡 / 专家气泡，与桌面端消息样式一致（`design/conversational_expert_collection.html` 的 `.msg.bot` / `.msg.user` 气泡样式可直接复用到移动端，只需要放大触控热区）
- **底部胶囊输入栏**：文字输入框 + 麦克风图标（同一行），这是 `docs/app-design.md` 里已经在网页/iOS 双端验证过的布局，直接复用

#### 4.3.1 三种输入方式（与 `docs/app-design.md` 第二节的"三种交互模式"一一对应，但语义按本产品调整）

| 模式 | 触发 | 行为 |
|---|---|---|
| 打字 | 直接在输入框打字 | 同桌面端，发送后走正常的一问一答采集流程 |
| **语音口述转文字**（主要语音入口） | 点输入栏麦克风图标 | 进入录音状态：取消(✕) / 波形动画 / 停止(■，整理后回填输入框可编辑) / 发送(↑，整理后直接作为一条消息发出）。复用 `web-demo` 已验证的"Realtime 转写 + `qwen-turbo` 一次性整理"链路（见 6.2） |
| **实时语音"对话"**（可选，Phase 2） | 长按/点击独立语音入口 | 专家连续说话，系统持续做增量转写，**AI 用文字回复**（不出声），本质是"语音口述"的连续化版本，不是 VoiceChat 那种语音全双工对话（对应 2.1 的决策） |

> 结合 2.1 的决策，"实时语音会话"和"语音口述转文字"在移动端**共用同一条底层链路**（转写→文本进入采集流程），差异只在于是"说一段发一条"还是"持续说、持续追问"，产品可以先只做前者（点麦克风→说→停止/发送），实时连续对话模式作为 Phase 2 增强，避免一次性做两套语音状态机。

#### 4.3.2 采集进度提示

对应桌面端 `.progress-panel`（阶段条 + 完成度百分比），移动端建议收进顶栏下方一条可展开的细进度条（默认只显示百分比 + 一句话摘要，点击展开显示 8 个阶段的完成状态），避免占用宝贵的竖屏空间。

### 4.4 DAG 页面设计（只读，可缩放）

#### 4.4.1 展示原则：美观直观优先

沿用桌面端右栏的克制视觉原则（`design/conversational_collection_design.md` 第20~21节）：不显示 `node_id`/`edge_id`/JSON/`confidence` 数字，只显示自然语言标签；颜色区分节点结构类型（活动/判断/并行/汇合/审批/起止），不用重型 BPMN 图标。

移动端在此基础上额外要求：

- **默认自动布局 + 自动居中缩放到刚好容纳整张图**（首次进入页面即可看清全貌，不需要先手动缩小）
- 双指捏合缩放、单指拖拽平移，缩放范围建议 0.3x–3x
- 节点在极小缩放级别下只显示图标+类型色块，放大到一定阈值后才显示文字标签，避免小屏幕上文字重叠糊成一团
- 点击节点：弹出底部半屏卡片（bottom sheet），展示该节点的自然语言描述、涉及角色、关联规则/经验判断——只读展示，卡片上不放"编辑""删除"按钮（对应 2.2）
- 点击空白处收起卡片；不提供节点拖拽

#### 4.4.2 页面内容分区（对应桌面右栏 A/B/C/D 四块，移动端纵向堆叠在图下方，随页面滚动）

1. 实时 DAG 图（占屏幕主要面积，见上）
2. 当前结构摘要（制造模式/行业/流程类型/结构特点，卡片形式）
3. 规则与经验（正式规则 / 现场经验，分开展示）
4. 待确认信息（最多 3–5 条，每条给出"回到会话说明"的提示文案，例如"回到会话里告诉我：谁最终批准恢复生产？"——移动端没有编辑入口，需要明确引导专家怎么处理待确认项）

### 4.5 移动端不做的事（明确排除，避免范围蔓延）

- DAG 节点/边的任何形式的移动端编辑（2.2 已确认）
- 移动端语音的 TTS 播报、语音打断、回声消除（2.1 已确认，这套机制留在 `web-demo` 的 VoiceChat 产品线里，本产品不复用）
- 移动端多任务/多流程并行采集（同一时刻只服务一个会话，与桌面端一致）
- 离线采集/断网续传（未讨论，若有需要请在评审时补充为独立需求）
- 数据集管理、Dashboard、实验中心（见 4.6）
- 任何形式的公网/互联网信息检索（见 4.7）

### 4.6 移动端功能边界：只做专家数据采集，不做实验功能

桌面端设计里，登录后的完整产品结构是"专家采集 / 数据集 / Dashboard / 实验中心"四大模块（`design/manufacturing_workflow_platform_design_v2.md` 第38节），但这四个模块的用户角色不同：专家采集面向一线专家本人，其余三个面向产品经理、算法与数据工程角色。

**移动浏览器端只实现"专家采集"这一个模块**，即本 PRD 第 4 节描述的会话页 + 历史抽屉 + DAG只读页。原因：

- 目标场景是专家在车间/产线现场用手机随手讲述工作经历，不是坐在电脑前做数据分析或配置实验参数
- 数据集导入预检、八维评估 Dashboard、实验卡片式参数配置这些操作本身信息密度高、依赖大量表格和图表，不适合小屏幕，勉强适配的性价比很低
- 桌面端的这三个模块保持现状不变，本次不做任何改动（呼应第 1.3 节的 Out of scope）

如果专家在移动端点击到需要这些能力的入口（理论上不应该出现，因为移动端顶层导航里本来就不放这三个模块的入口），应引导"请在电脑浏览器中打开"，而不是做一个阉割版的移动界面。

### 4.7 产品边界：封闭域采集，不接入公网搜索

本产品的采集对象是**专家亲身经历的真实工作**，AI 引导模型的职责边界在第 3.2 节已经很明确——只做"引导、复述、澄清、结构化抽取"，不允许"猜测未说出的事实""自动补 SOP"。这条原则延伸到网络能力上就是：

- **AI 引导模型不联网检索**，不会为了"补全流程""验证专家说法"或"查找同类案例"去搜索互联网
- 会话上下文只包含：当前会话的历史轮次、已确认事实、当前 DAG 摘要（见第 3.5 节 LLM 输入设计），不注入任何外部检索结果
- 这一条是**对 `docs/app-design.md` 第六节"过渡语（filler phrases）"规划的明确排除**：那份文档为 VoiceChat（本仓库另一个语音助手产品）规划了"未来接入外部工具调用（如新闻搜索）时，用预置过渡语掩盖网络延迟"的方案；本产品不做任何外部工具调用，因此**不需要过渡语机制**，也不需要该文档里讨论的"工具调用中先说一句预设文本"这类设计
- 移动端语音链路只复用 `web-demo` 里"语音转写"这一段能力（见 6.2），刻意不复用其未来可能扩展的外部检索/工具调用相关规划

若未来产品方向变化、确实需要引入公网信息（例如比对行业标准文档），应作为独立的新需求评审，不在本次 PRD 范围内，且需要重新评估"专家真实经历 vs 外部引用信息"在数据集 `provenance.source_type` 上如何区分（避免污染 `expert_collected` 数据的真实性，参见 `design/dataset_design_spec.md` 第五维度"真实性与来源可信度"）。

## 5. 交互与导航规范

### 5.1 顶层导航结构

```
移动端 App Shell
├─ 会话页（主页，默认进入）
│   └─ 顶栏左上角「☰」→ 历史流程抽屉（覆盖层）
│   └─ 主体右滑 → DAG 页
├─ DAG 页
│   └─ 顶栏左上角「←」或左滑 → 返回会话页
└─ 历史流程抽屉（覆盖层，非独立页面）
    └─ 点击流程项 → 关闭抽屉 + 会话页切换到该流程会话
    └─ 「+ 新建一个流程」→ 关闭抽屉 + 会话页重置为空会话
```

### 5.2 与桌面端的一致性要求

移动端和桌面端必须是**同一个会话状态的两种视图**，不是两套独立实现：
- 专家在桌面端进行到一半的流程，切换到手机浏览器打开同一账号，应能在历史抽屉里看到并继续（依赖后端 `GET /api/expert-workflows/{id}` 恢复会话，见第 6.4 节，接口本身不需要区分端）
- DAG 数据模型、Graph Ops、Validator 规则**完全复用桌面端**（第 3.3、3.4 节），移动端只是视图和交互层的差异，不是另起一套数据结构

### 5.3 触控热区与可用性

- 消息气泡、输入框、麦克风按钮、DAG 节点点击热区均不小于 44×44px（iOS HIG 标准）
- 语音录音状态的三个按钮（✕/■/↑）之间保持足够间距，避免车间场景下专家可能戴手套/手不够灵活导致误触

### 5.4 右滑切换手势规范（对应 2.3 的决策，给出可落地的实现细节）

- 判定区域：距屏幕左边缘 `< 20px` 的起始触摸点**不触发**页面切换手势（让给系统返回手势），仅当起始点在 `≥ 20px` 区域时，检测到水平位移 > 垂直位移且超过阈值（建议 60–80px）才触发从会话页→DAG页的切换动画
- DAG 页返回会话页：支持左滑（同样排除左边缘判定区，改为不限制，因为此时是"从右向左滑回主页"，不与系统返回手势冲突）+ 顶栏返回按钮兜底，两种方式都要有，不能只依赖手势
- 语音录音状态下（波形动画显示中）**临时禁用左右滑动切换页面手势**，避免专家说话时手指误触导致页面跳转
- 切换动效：跟随手指位移的卡片式平移过渡（类似原生 App 的页面切换），不做生硬的整页切换，让专家有"这是同一个会话的另一面"的心智，而不是"跳到了另一个功能"

## 6. 技术方案要点

### 6.1 前端框架与图渲染

- 沿用桌面端已确定方案：**React Flow + ELK.js** 做自动布局（`design/conversational_collection_design.md` 第31节），移动端复用同一套渲染引擎，不重新选型
- 移动端追加：React Flow 内置的 `zoomOnPinch`/`panOnDrag` 配置即可满足只读缩放平移需求，不需要额外引入手势库
- 页面切换（会话页 ↔ DAG页）的手势识别建议用轻量方案（如 `react-use-gesture` 或原生 `touchstart/move/end` + CSS transform），不引入完整的路由级别转场框架，保持和现有技术栈一致

### 6.2 语音链路（复用 web-demo 已验证的机制，不重新造轮子）

依据本仓库 `docs/app-design.md` 第三节已经在 web 端验证过的方案：

1. **语音识别**：复用 Realtime WebSocket 连接的 `conversation.item.input_audio_transcription.completed` 事件拿到转写文本，**但不触发语音回复**（这与 `web-demo` 现有的"语音口述转文字"模式技术上完全一致，可直接复用其连接建立、音频采集、转写事件处理代码）
2. **AI 整理**（可选）：桌面端 DAG 采集本身就需要 AI 对每一轮输入做结构化抽取，如果专家的口语转写已经足够清晰，可以跳过"整理成书面语"这一步、直接把转写文本送进采集流程的 7B 引导模型；是否需要先过一次 `qwen-turbo` 清理（如 `web-demo` 的口述转文字方案）取决于实测转写质量，建议先用未经整理的原始转写接入 7B 引导模型测试效果，效果不佳再引入整理步骤，避免过早增加一次网络往返
3. **不需要**：TTS 播放、`response.cancel` 打断机制、回声消除（AEC）三处 `getUserMedia` 约束——这些是 `web-demo` VoiceChat 模式的专属机制，本产品因为 2.1 的决策不需要

### 6.3 响应式断点

- 复用桌面端媒体查询断点思路（`design/conversational_expert_collection.html` 已有 `900px` 断点将三栏收为纵向堆叠），移动端 PRD 明确要求：**`< 900px` 不是"三栏堆叠"，而是切换为本文档第4节描述的"两页+抽屉"结构**，需要前端按两套布局逻辑实现，而不是简单的 CSS 媒体查询堆叠（现有 HTML 原型里 `@media(max-width:900px){.app{display:block}}` 这种堆叠方案不满足本次移动端需求，仅作为过渡态参考）

### 6.4 后端接口影响

移动端不新增数据模型，仅复用桌面端已设计的接口（`design/conversational_collection_design.md` 第32节）：

- `GET /api/expert-workflows`：历史流程抽屉列表
- `GET /api/expert-workflows/{id}`：恢复会话（含跨端续接）
- `POST /api/expert-workflows/{id}/turns`：发送专家回答（文字或语音转写文本，接口不区分来源）
- `GET /api/expert-workflows/{id}` 返回的 `current_dag` 直接喂给移动端 DAG 只读渲染，无需新增只读专用接口
- 语音转写走 Realtime WebSocket，与文字消息是两条不同链路，但转写完成后统一通过 `POST .../turns` 提交文本，后端不需要感知"这条消息是不是语音来的"

## 7. 需要你裁定的设计冲突（重要，请优先处理）

整理资料时发现两份设计文档在核心数据模型上有分歧，会直接影响 Schema、Validator 和后续数据集/实验层的一致性，建议在开发前明确口径：

### 7.1 返工/重试的表达方式：DAG-only + retry_semantics，还是允许 loop_back 边？

- `design/conversational_collection_design.md`（v2.1，较新）主张：**主图必须是合法 DAG，不允许 `loop_back` 边**，返工统一用节点上的 `retry_semantics` 字段表达（第3、18节）
- `design/manufacturing_workflow_platform_design_v2.md`（更早）+ `schema/workflow_graph_schema_v2.json` + `schema/workflow_graph_v2_sample.json` 里，Edge 类型**明确包含 `loop_back`**，且样例数据 `wf_graph_0001` 里 `e12` 就是一条 `from: n9, to: n5, edge_type: loop_back` 的真实回边，`graph_type` 字段也确实支持标记 `directed_graph`（区别于 `dag`）

两种方案都自洽，但不能同时作为"当前生效方案"——如果按 v2.1 的 DAG-only 口径开发采集层，那么现有的 `workflow_graph_schema_v2.json` 和样例数据就需要同步修订（把 `loop_back` 边改写成 `retry_semantics`）；如果保留 `loop_back` 边，则 v2.1 文档里"主 DAG 不含环"的一系列 Validator 规则（第17节"新增 Edge 后不得形成 cycle"）需要放宽为"仅在特定 `graph_type` 下要求无环"。

**建议**：采用 v2.1（DAG-only + retry_semantics）作为本次移动/桌面采集层的唯一口径——原因是它能保证图始终可拓扑排序，便于移动端"自动布局 + 自动居中"这类依赖 DAG 层级结构的渲染逻辑稳定工作；但这意味着 `schema/` 目录下两份文件需要在正式开发前由你确认是否同步更新。本 PRD 暂不擅自修改 schema 文件，留待你确认。

### 7.2 节点类型集合的差异

v2.1 的 MVP 节点集合比更早版本少了 `event`、`subprocess`（v2.1 第10节标注为"后续可扩展"），而 `schema/workflow_graph_schema_v2.json` 已经把两者列为正式支持类型。若按 v2.1 做 Phase A/B 的 MVP，需要明确：Schema 里已经存在但产品暂不采集的字段，是保留在 Schema 里"允许但本期不产出"，还是本期就直接支持。建议保留在 Schema 里但采集 UI 暂不引导专家产出，两者不冲突，只是需要在 Graph Validator 里确认不会因为"缺失 `event`/`subprocess` 相关字段"而报错。

## 8. 验收标准（在桌面端已有标准基础上补充移动端条目）

### 8.1 专家体验（桌面 + 移动共用）

- 不出现强制 DAG/BPMN 术语
- 专家可以只用自然语言（含语音）完成采集
- 分支、并行、汇合能被正确追问
- 图形界面专家能看懂（移动端额外要求：默认缩放级别下一眼看清全貌）
- 专家可以纠错（移动端：纠错入口收敛在会话页，DAG页有明确的"回会话说"引导文案）

### 8.2 移动端专项验收

- [ ] 主页默认展示会话页，非历史列表页
- [ ] 左上角列表图标点击后正确弹出历史流程抽屉，且抽屉内容与桌面端左栏字段一致（名称/行业/场景/状态/完成度/更新时间）
- [ ] 非边缘区域右滑正确切换到 DAG 页，边缘 20px 区域内起始的滑动不触发页面切换（不与浏览器返回手势冲突，需在 iOS Safari、Chrome Android 上实测）
- [ ] DAG 页支持双指缩放、单指平移，首次进入自动适配全图
- [ ] DAG 页所有交互均为只读，不出现任何编辑入口
- [ ] 语音口述转文字的取消/停止/发送三个状态按钮在移动端触控下正常工作，且识别文本正确进入采集轮次
- [ ] 语音输入过程中，左右滑动切换页面的手势被临时禁用
- [ ] 同一账号在桌面端和移动浏览器间切换，能看到同一会话的最新状态（DAG、完成度、待确认项一致）

### 8.3 数据与 AI（复用第3.3、3.4节标准，不因移动端而降低要求）

- 输出是合法 DAG，可拓扑排序（若第7.1节确认沿用 v2.1 口径）
- 所有自动抽取都有 `source_turn_ids` 证据
- AI 不静默补写事实、不静默解决冲突

## 9. 里程碑建议

在桌面端已有的 Phase A/B/C（`design/conversational_collection_design.md` 第34节）基础上，追加移动端阶段：

| 阶段 | 内容 |
|---|---|
| Phase A（桌面，沿用原计划） | 三栏界面、历史流程、会话、DAG节点/边/分支/并行/汇合、实时右栏图、Validator、专家确认 |
| Phase B（桌面，沿用原计划） | 规则/经验、Artifact、交接、审批、返工语义、会话冲突处理 |
| **Phase M1（移动，新增）** | 会话页（文字输入）+ 历史抽屉 + DAG只读页（缩放平移，不含语音） —— 先跑通移动端的两页导航与只读图渲染 |
| **Phase M2（移动，新增）** | 接入语音口述转文字（取消/停止/发送三态），完成 8.2 节验收 |
| **Phase M3（移动，可选增强）** | "实时语音对话"连续追问模式（4.3.1 表格中的第三种输入方式） |
| Phase C（沿用原计划） | 自动质量评估、Gold Annotation、多专家复核、数据集版本、实验直接联动 |

建议 Phase M1/M2 在桌面 Phase A 基本稳定（DAG 数据模型、Graph Ops、Validator 已跑通）之后再启动，因为移动端复用的是同一套后端和数据模型，先在桌面端把模型跑稳可以避免移动端返工。
