## 1. 背景与目标

### 1.1 要解决的问题

现有的制造专家知识主要停留在专家脑子里，缺少结构化、可追溯、可用于 AI 训练/实验的采集方式。人工画流程图（BPMN/DAG）对制造专家有极高的学习门槛，因此产品的核心主张是：

> **专家只需要像聊天一样，讲自己真实做过的一件工作；系统负责把自然语言实时整理成结构化的工作流图（Graph），专家只需要确认和纠错，不需要学习任何建模术语。**

### 1.2 目标用户

MES/车间管理、质量、设备、工艺、计划、IE、精益生产等制造专家。采集入口面向专家本人，管理/研究侧（数据集、Dashboard、实验中心）面向产品经理、算法与数据工程角色，不在本次移动端改造范围内。

### 1.3 本次 PRD 的范围

- **In scope**：
  - 专家会话式采集的桌面端产品需求盘点（已有设计的结构化整理） + 移动浏览器端新增体验设计（会话主页、语音输入、DAG 只读查看）——第 1～10 节
  - **DAG 可视化重新设计**（第 11 节）：原有 `design/*.html` 原型只作参考，本 PRD 重新给出美观直观、面向非专业人士的视觉与交互规范，桌面右栏与移动 DAG 页统一采用
  - **数据集导入导出**（第 12 节）：正式收编进本 PRD，在 `design/dataset_design_spec.md`、`design/manufacturing_workflow_platform_design_v2.md` 第16~21节基础上补全为可开发的功能设计
  - **Dashboard 完整设计**（第 13 节）：含数据集质量评价（八维评估 + Graph 专用质量指标）
  - **实验中心设计**（第 14 节）：新增"实验结果详细文字解释"能力（原有设计只有量化指标表格，没有面向人的解读）
  - **LLM 使用清单**（第 15 节）：直接回答"本产品哪些环节需要 LLM"这个问题，供你评估
  - **管理页面**（第 16 节，本轮新增）：用户与权限、数据集发布/Gold 版本、删除归档、审计日志
- **不做**：
  - 移动端 DAG 图的编辑能力（本次评审已确认，见 2.2）
  - **移动端不提供实验中心入口**：手机浏览器端只服务"专家数据采集"这一件事（会话页 + 历史抽屉 + DAG只读页），不做数据集管理、Dashboard、实验中心、管理页面的移动适配，这四块继续保持桌面专属（详见 1.4、4.6）
  - **不接入公网/互联网搜索**：本产品是**封闭域**的数据采集与实验平台，专家讲述的是自己真实经历的工作，AI 引导模型也只基于会话上下文做澄清追问，不联网检索资料、不做事实核查、不引用外部网页。这一条**是对 `docs/app-design.md`（本仓库既有的 VoiceChat/web-demo 语音产品设计）里规划中的"过渡语 + 未来接入新闻搜索等外部工具调用"能力的明确排除**——那是另一个产品（VoiceChat 日常语音助手）的规划方向，本产品不继承（详见 4.7）

### 1.4 端与端的功能边界（再次强调，作为全文的唯一权威口径）

这条边界在第 4.6 节已经定过，这里再次置顶强调，因为它决定了第 11～16 节里每个新模块该不该做移动适配：

| | 桌面浏览器端 | 手机浏览器端 |
|---|---|---|
| 专家会话式采集（问答 + DAG查看） | ✅ | ✅ 唯一支持的功能 |
| 数据集管理（导入导出，第 12 节） | ✅ | ❌ |
| Dashboard（第 13 节） | ✅ | ❌ |
| 实验中心（第 14 节） | ✅ | ❌ |
| 管理页面（第 16 节） | ✅ | ❌ |

**桌面浏览器端是全部功能的唯一完整入口**；**手机浏览器端仅支持专家问答（采集会话 + 只读 DAG 查看）**，不是"阉割版"其他模块，而是这些模块从产品定义上就不出现在移动端的导航里（呼应 4.6 节"如果专家在移动端点击到需要这些能力的入口，应引导'请在电脑浏览器中打开'"）。第 12～16 节的所有页面设计，默认场景都是桌面浏览器，除非特别注明。

## 2. 移动端需求：已确认的产品决策

这三条是本次讨论中明确拍板的，作为后续所有移动端设计的前提，不再反复讨论：

### 2.1 语音回复形式：文字为主

移动端「实时语音会话」中，专家可以语音说话，但 **AI 的回复以文字气泡呈现，不做语音播报（TTS）**。语音只是一种输入方式，采集节奏和桌面端的追问逻辑完全一致。

- 不引入 TTS、打断、回声消除等语音播报相关机制，大幅降低移动端实现成本
- 更适合车间等嘈杂环境下的实际使用场景（专家不方便一直听语音回复）
- 与本仓库 `web-demo` 里已经验证过的"实时语音全双工对话"（VoiceChat 模式）是**两回事**，本产品移动端复用的是 `web-demo` 中"语音识别转写"这一段能力（Realtime 协议的 `input_audio_transcription`），不复用其语音播放/打断/回声消除那一整套机制

### 2.2 移动端 DAG 页面：完全只读

右滑看到的 DAG 页面在移动端**只用于查看和确认，不支持编辑**。所有纠错（改节点文字、改分支条件、标记"这里不对"等）都必须回到会话页面，用自然语言说出来，由 AI 转成 Graph Ops 后由后端校验生效。

- 移动端不需要实现拖拽节点、点击编辑表单等触控交互，只需要实现"缩放 + 平移 + 点节点看详情（只读弹层）"
- 这与桌面端设计（`design/conversational_collection_design.md` 第22节、`design/manufacturing_workflow_platform_design_v2.md` 第10.2节）形成明确分工：**桌面端保留完整的点图纠错能力，移动端纠错入口收敛回会话**

### 2.3 右滑手势：非边缘区域触发

主屏幕（会话页）向右滑动切换到 DAG 页面，**判定区域必须排除屏幕左边缘约 20px 的系统手势保留区**，避免与 iOS Safari / 主流移动浏览器"从屏幕边缘右滑 = 返回上一页"的系统手势冲突。

- 具体交互规范见第 5.4 节

## 3. 现状盘点：桌面端设计（已有，本次整理归档）

以下内容来自 `design/conversational_collection_design.md`（v2.1，DAG-first）与 `design/manufacturing_workflow_platform_design_v2.md`（更早版本的完整平台说明书），两者对采集层的设计基本一致，本节做统一整理，作为移动端设计的对照基准。桌面端本次**不做改动**。

### 3.1 页面结构

固定竖向三栏（桌面宽度 ≥ 1180px 体验最佳）：

| 分栏 | 内容 | 建议宽度 |
|---|---|---|
| 左栏 | 历史流程清单（专家过去回答过的所有流程，可继续/复制/搜索/筛选） | 240–280px |
| 主栏 | 会话式采集（AI ↔ 专家，自然语言输入） | 自适应，占最大空间 |
| 右栏 | 实时 DAG 图 + 结构化摘要 + 规则/经验 + 待确认项 | 400–460px |

### 3.2 采集原则

1. **不问术语，只问业务**：不出现"分支""并行""汇合""DAG""Loop Back"这些词，全部转成自然语言问句（例如"这两件事是先后做，还是可以同时做？"）
2. **7B 引导模型的职责边界**：只负责引导、复述、澄清、结构化抽取、选择下一条最有价值的追问；**不允许**猜测未说出的事实、自动补 SOP、编造角色/阈值、为了图完整而创造节点/边、静默解决冲突
3. **不是固定 Wizard**：内部分 8 个采集阶段（触发发现→主干发现→分支发现→并行汇合发现→角色系统发现→规则经验发现→结束条件发现→专家复核），但专家提前说出后面信息时立即提取，不强制按顺序问
4. **每轮只问一个最重要的问题**（优先级 P0 主干 → P1 分支 → P2 并行 → P3 汇合 → P4 审批/交接 → P5 返工重试 → P6 规则经验 → P7 研究增强）

### 3.3 DAG 数据模型要点

- 节点类型：`start / activity / decision / parallel_split / parallel_join / merge / approval / handoff / wait / end`（后续可扩展 `event / subprocess`）
- 边类型：`normal / conditional / parallel / merge / handoff / approval / timeout / exception_forward`
- **返工/重试不建边**，而是作为节点的 `retry_semantics` 语义附加信息保存，保证主图始终是合法 DAG，可稳定拓扑排序（这是 v2.1 版本相对更早版本的关键升级，详见第 7 节的口径冲突说明）
- 每个节点/边必须保留 `source_turn_ids`（证据可追溯）、`confidence`、`expert_confirmed`——模型抽取结果不等于已确认事实

### 3.4 冲突处理

前后表述矛盾时（例如"质量主管批准"vs"班组长决定"），系统不得静默覆盖，必须生成 `conflicts` 并追问澄清。

### 3.5 完成度与提交

- Completion Score 按 9 个维度加权（Trigger 10% / 主干 20% / 分支条件 15% / 并行汇合 15% / 角色交接 10% / 系统证据 5% / 规则经验 10% / 结束条件 10% / 专家确认 5%），流程本身没有分支/并行时权重重新分配到主干和结束条件，不扣分
- `>= 80` 进入最终确认；最终确认页面停止主动追问，专家看完整 DAG 后点"确认并提交"或"继续修改"
- 提交后保存四份数据：原始转写、DAG图JSON、归一化图JSON、会话抽取轨迹；已提交流程再次修改生成新版本，不覆盖旧版本

## 4. 新增需求：移动浏览器端体验设计

### 4.1 设计原则

移动端不是桌面三栏的简单压缩，而是围绕"专家最可能在车间/产线现场、边走边说"这个使用场景重新设计交互，同时最大程度复用本仓库 `web-demo/`（VoiceChat 语音对话产品）已经验证过的移动端语音交互范式（胶囊输入栏、语音波形状态、口述转文字三按钮），不重新发明一套语音 UI。

### 4.2 页面结构：两页 + 一个抽屉

```
┌─────────────────────────┐        ┌─────────────────────────┐
│  ☰  CNC尺寸超差处理   ⓘ │  右滑→ │  ←  当前整理出的流程     │
│                          │  ←左滑 │                          │
│      会话页（主页）      │        │      DAG 只读查看页      │
│   AI ↔ 专家对话气泡      │        │   可缩放 / 可平移        │
│                          │        │   点节点看详情           │
│  [胶囊输入栏 + 麦克风]   │        │   底部：结构摘要/待确认  │
└─────────────────────────┘        └─────────────────────────┘
        ↑ 点击左上角 ☰
┌─────────────────────────┐
│  我的流程          ✕    │
│  ─────────────────────  │
│  CNC尺寸超差处理  67%    │  （对应桌面端左栏）
│  夜班缺料补料流程 已确认  │
│  换型首件确认      35%   │
│  + 新建一个流程          │
└─────────────────────────┘
```

- **会话页 = 移动端默认主页**（对应桌面端主栏），这是这次改动里最关键的一条：移动端不是"三栏挤成一栏后第一屏是历史列表"，而是**直接进入当前会话**，历史列表退居为左上角抽屉，与桌面端"专家一进来就该继续/开始讲述"的产品心智保持一致
- **左上角列表图标（☰）**：点开后从左侧滑出历史流程抽屉（对应桌面左栏的全部功能：搜索、状态筛选、场景筛选、新建流程、复制变体、删除草稿），覆盖在会话页之上，点击遮罩或流程项关闭抽屉
- **主页右滑 → DAG 页**：对应桌面右栏，只读查看（见 2.2、5.4）
- 顶部栏右侧的 ⓘ / `···` 可以放"检查流程完整度"入口（对应桌面右栏顶部"检查流程"按钮），不做成常驻面板，避免挤占会话区域

### 4.3 会话页设计（借鉴 web-demo 的语音交互范式）

移动端会话页的视觉与交互方向直接复用 `docs/app-design.md` 第一节已经验证过的"ChatGPT App 风格"设计语言，而不是重新设计一套：

- 极简顶栏：左侧列表图标 + 中间流程名（或"新的流程"）+ 右侧辅助入口，无大标题栏
- 对话区：AI 气泡 / 专家气泡，与桌面端消息样式一致（`design/conversational_expert_collection.html` 的 `.msg.bot` / `.msg.user` 气泡样式可直接复用到移动端，只需要放大触控热区）
- **底部胶囊输入栏**：文字输入框 + 麦克风图标（同一行），这是 `docs/app-design.md` 里已经在网页/iOS 双端验证过的布局，直接复用

#### 4.3.1 三种输入方式（与 `docs/app-design.md` 第二节的"三种交互模式"一一对应，但语义按本产品调整）

| 模式 | 触发 | 行为 |
|---|---|---|
| 打字 | 直接在输入框打字 | 同桌面端，发送后走正常的一问一答采集流程 |
| **语音口述转文字**（主要语音入口） | 点输入栏麦克风图标 | 进入录音状态：取消(✕) / 波形动画 / 停止(■，整理后回填输入框可编辑) / 发送(↑，整理后直接作为一条消息发出）。复用 `web-demo` 已验证的"Realtime 转写 + `qwen-turbo` 一次性整理"链路（见 6.2） |
| **实时语音"对话"**（可选，Phase 2） | 长按/点击独立语音入口 | 专家连续说话，系统持续做增量转写，**AI 用文字回复**（不出声），本质是"语音口述"的连续化版本，不是 VoiceChat 那种语音全双工对话（对应 2.1 的决策） |

> 结合 2.1 的决策，"实时语音会话"和"语音口述转文字"在移动端**共用同一条底层链路**（转写→文本进入采集流程），差异只在于是"说一段发一条"还是"持续说、持续追问"，产品可以先只做前者（点麦克风→说→停止/发送），实时连续对话模式作为 Phase 2 增强，避免一次性做两套语音状态机。

#### 4.3.2 采集进度提示

对应桌面端 `.progress-panel`（阶段条 + 完成度百分比），移动端建议收进顶栏下方一条可展开的细进度条（默认只显示百分比 + 一句话摘要，点击展开显示 8 个阶段的完成状态），避免占用宝贵的竖屏空间。

### 4.4 DAG 页面设计（只读，可缩放）

#### 4.4.1 展示原则：美观直观优先

沿用桌面端右栏的克制视觉原则（`design/conversational_collection_design.md` 第20~21节）：不显示 `node_id`/`edge_id`/JSON/`confidence` 数字，只显示自然语言标签；颜色区分节点结构类型（活动/判断/并行/汇合/审批/起止），不用重型 BPMN 图标。

移动端在此基础上额外要求：

- **默认自动布局 + 自动居中缩放到刚好容纳整张图**（首次进入页面即可看清全貌，不需要先手动缩小）
- 双指捏合缩放、单指拖拽平移，缩放范围建议 0.3x–3x
- 节点在极小缩放级别下只显示图标+类型色块，放大到一定阈值后才显示文字标签，避免小屏幕上文字重叠糊成一团
- 点击节点：弹出底部半屏卡片（bottom sheet），展示该节点的自然语言描述、涉及角色、关联规则/经验判断——只读展示，卡片上不放"编辑""删除"按钮（对应 2.2）
- 点击空白处收起卡片；不提供节点拖拽

#### 4.4.2 页面内容分区（对应桌面右栏 A/B/C/D 四块，移动端纵向堆叠在图下方，随页面滚动）

1. 实时 DAG 图（占屏幕主要面积，见上）
2. 当前结构摘要（制造模式/行业/流程类型/结构特点，卡片形式）
3. 规则与经验（正式规则 / 现场经验，分开展示）
4. 待确认信息（最多 3–5 条，每条给出"回到会话说明"的提示文案，例如"回到会话里告诉我：谁最终批准恢复生产？"——移动端没有编辑入口，需要明确引导专家怎么处理待确认项）

### 4.5 移动端不做的事（明确排除，避免范围蔓延）

- DAG 节点/边的任何形式的移动端编辑（2.2 已确认）
- 移动端语音的 TTS 播报、语音打断、回声消除（2.1 已确认，这套机制留在 `web-demo` 的 VoiceChat 产品线里，本产品不复用）
- 移动端多任务/多流程并行采集（同一时刻只服务一个会话，与桌面端一致）
- 离线采集/断网续传（未讨论，若有需要请在评审时补充为独立需求）
- 数据集管理、Dashboard、实验中心（见 4.6）
- 任何形式的公网/互联网信息检索（见 4.7）

### 4.6 移动端功能边界：只做专家数据采集，不做实验功能

桌面端设计里，登录后的完整产品结构是"专家采集 / 数据集 / Dashboard / 实验中心"四大模块（`design/manufacturing_workflow_platform_design_v2.md` 第38节），但这四个模块的用户角色不同：专家采集面向一线专家本人，其余三个面向产品经理、算法与数据工程角色。

**移动浏览器端只实现"专家采集"这一个模块**，即本 PRD 第 4 节描述的会话页 + 历史抽屉 + DAG只读页。原因：

- 目标场景是专家在车间/产线现场用手机随手讲述工作经历，不是坐在电脑前做数据分析或配置实验参数
- 数据集导入预检、八维评估 Dashboard、实验卡片式参数配置这些操作本身信息密度高、依赖大量表格和图表，不适合小屏幕，勉强适配的性价比很低
- 桌面端的这三个模块保持现状不变，本次不做任何改动（呼应第 1.3 节的 Out of scope）

如果专家在移动端点击到需要这些能力的入口（理论上不应该出现，因为移动端顶层导航里本来就不放这三个模块的入口），应引导"请在电脑浏览器中打开"，而不是做一个阉割版的移动界面。

### 4.7 产品边界：封闭域采集，不接入公网搜索

本产品的采集对象是**专家亲身经历的真实工作**，AI 引导模型的职责边界在第 3.2 节已经很明确——只做"引导、复述、澄清、结构化抽取"，不允许"猜测未说出的事实""自动补 SOP"。这条原则延伸到网络能力上就是：

- **AI 引导模型不联网检索**，不会为了"补全流程""验证专家说法"或"查找同类案例"去搜索互联网
- 会话上下文只包含：当前会话的历史轮次、已确认事实、当前 DAG 摘要（见第 3.5 节 LLM 输入设计），不注入任何外部检索结果
- 这一条是**对 `docs/app-design.md` 第六节"过渡语（filler phrases）"规划的明确排除**：那份文档为 VoiceChat（本仓库另一个语音助手产品）规划了"未来接入外部工具调用（如新闻搜索）时，用预置过渡语掩盖网络延迟"的方案；本产品不做任何外部工具调用，因此**不需要过渡语机制**，也不需要该文档里讨论的"工具调用中先说一句预设文本"这类设计
- 移动端语音链路只复用 `web-demo` 里"语音转写"这一段能力（见 6.2），刻意不复用其未来可能扩展的外部检索/工具调用相关规划

若未来产品方向变化、确实需要引入公网信息（例如比对行业标准文档），应作为独立的新需求评审，不在本次 PRD 范围内，且需要重新评估"专家真实经历 vs 外部引用信息"在数据集 `provenance.source_type` 上如何区分（避免污染 `expert_collected` 数据的真实性，参见 `design/dataset_design_spec.md` 第五维度"真实性与来源可信度"）。

## 5. 交互与导航规范

### 5.1 顶层导航结构

```
移动端 App Shell
├─ 会话页（主页，默认进入）
│   └─ 顶栏左上角「☰」→ 历史流程抽屉（覆盖层）
│   └─ 主体右滑 → DAG 页
├─ DAG 页
│   └─ 顶栏左上角「←」或左滑 → 返回会话页
└─ 历史流程抽屉（覆盖层，非独立页面）
    └─ 点击流程项 → 关闭抽屉 + 会话页切换到该流程会话
    └─ 「+ 新建一个流程」→ 关闭抽屉 + 会话页重置为空会话
```

### 5.2 与桌面端的一致性要求

移动端和桌面端必须是**同一个会话状态的两种视图**，不是两套独立实现：
- 专家在桌面端进行到一半的流程，切换到手机浏览器打开同一账号，应能在历史抽屉里看到并继续（依赖后端 `GET /api/expert-workflows/{id}` 恢复会话，见第 6.4 节，接口本身不需要区分端）
- DAG 数据模型、Graph Ops、Validator 规则**完全复用桌面端**（第 3.3、3.4 节），移动端只是视图和交互层的差异，不是另起一套数据结构

### 5.3 触控热区与可用性

- 消息气泡、输入框、麦克风按钮、DAG 节点点击热区均不小于 44×44px（iOS HIG 标准）
- 语音录音状态的三个按钮（✕/■/↑）之间保持足够间距，避免车间场景下专家可能戴手套/手不够灵活导致误触

### 5.4 右滑切换手势规范（对应 2.3 的决策，给出可落地的实现细节）

- 判定区域：距屏幕左边缘 `< 20px` 的起始触摸点**不触发**页面切换手势（让给系统返回手势），仅当起始点在 `≥ 20px` 区域时，检测到水平位移 > 垂直位移且超过阈值（建议 60–80px）才触发从会话页→DAG页的切换动画
- DAG 页返回会话页：支持左滑（同样排除左边缘判定区，改为不限制，因为此时是"从右向左滑回主页"，不与系统返回手势冲突）+ 顶栏返回按钮兜底，两种方式都要有，不能只依赖手势
- 语音录音状态下（波形动画显示中）**临时禁用左右滑动切换页面手势**，避免专家说话时手指误触导致页面跳转
- 切换动效：跟随手指位移的卡片式平移过渡（类似原生 App 的页面切换），不做生硬的整页切换，让专家有"这是同一个会话的另一面"的心智，而不是"跳到了另一个功能"

## 6. 技术方案要点

### 6.1 前端框架与图渲染

- 沿用桌面端已确定方案：**React Flow + ELK.js** 做自动布局（`design/conversational_collection_design.md` 第31节），移动端复用同一套渲染引擎，不重新选型
- 移动端追加：React Flow 内置的 `zoomOnPinch`/`panOnDrag` 配置即可满足只读缩放平移需求，不需要额外引入手势库
- 页面切换（会话页 ↔ DAG页）的手势识别建议用轻量方案（如 `react-use-gesture` 或原生 `touchstart/move/end` + CSS transform），不引入完整的路由级别转场框架，保持和现有技术栈一致

### 6.2 语音链路（复用 web-demo 已验证的机制，不重新造轮子）

依据本仓库 `docs/app-design.md` 第三节已经在 web 端验证过的方案：

1. **语音识别**：复用 Realtime WebSocket 连接的 `conversation.item.input_audio_transcription.completed` 事件拿到转写文本，**但不触发语音回复**（这与 `web-demo` 现有的"语音口述转文字"模式技术上完全一致，可直接复用其连接建立、音频采集、转写事件处理代码）
2. **AI 整理**（可选）：桌面端 DAG 采集本身就需要 AI 对每一轮输入做结构化抽取，如果专家的口语转写已经足够清晰，可以跳过"整理成书面语"这一步、直接把转写文本送进采集流程的 7B 引导模型；是否需要先过一次 `qwen-turbo` 清理（如 `web-demo` 的口述转文字方案）取决于实测转写质量，建议先用未经整理的原始转写接入 7B 引导模型测试效果，效果不佳再引入整理步骤，避免过早增加一次网络往返
3. **不需要**：TTS 播放、`response.cancel` 打断机制、回声消除（AEC）三处 `getUserMedia` 约束——这些是 `web-demo` VoiceChat 模式的专属机制，本产品因为 2.1 的决策不需要

### 6.3 响应式断点

- 复用桌面端媒体查询断点思路（`design/conversational_expert_collection.html` 已有 `900px` 断点将三栏收为纵向堆叠），移动端 PRD 明确要求：**`< 900px` 不是"三栏堆叠"，而是切换为本文档第4节描述的"两页+抽屉"结构**，需要前端按两套布局逻辑实现，而不是简单的 CSS 媒体查询堆叠（现有 HTML 原型里 `@media(max-width:900px){.app{display:block}}` 这种堆叠方案不满足本次移动端需求，仅作为过渡态参考）

### 6.4 后端接口影响

移动端不新增数据模型，仅复用桌面端已设计的接口（`design/conversational_collection_design.md` 第32节）：

- `GET /api/expert-workflows`：历史流程抽屉列表
- `GET /api/expert-workflows/{id}`：恢复会话（含跨端续接）
- `POST /api/expert-workflows/{id}/turns`：发送专家回答（文字或语音转写文本，接口不区分来源）
- `GET /api/expert-workflows/{id}` 返回的 `current_dag` 直接喂给移动端 DAG 只读渲染，无需新增只读专用接口
- 语音转写走 Realtime WebSocket，与文字消息是两条不同链路，但转写完成后统一通过 `POST .../turns` 提交文本，后端不需要感知"这条消息是不是语音来的"

## 7. 需要你裁定的设计冲突（重要，请优先处理）

整理资料时发现两份设计文档在核心数据模型上有分歧，会直接影响 Schema、Validator 和后续数据集/实验层的一致性，建议在开发前明确口径：

### 7.1 返工/重试的表达方式：DAG-only + retry_semantics，还是允许 loop_back 边？

- `design/conversational_collection_design.md`（v2.1，较新）主张：**主图必须是合法 DAG，不允许 `loop_back` 边**，返工统一用节点上的 `retry_semantics` 字段表达（第3、18节）
- `design/manufacturing_workflow_platform_design_v2.md`（更早）+ `schema/workflow_graph_schema_v2.json` + `schema/workflow_graph_v2_sample.json` 里，Edge 类型**明确包含 `loop_back`**，且样例数据 `wf_graph_0001` 里 `e12` 就是一条 `from: n9, to: n5, edge_type: loop_back` 的真实回边，`graph_type` 字段也确实支持标记 `directed_graph`（区别于 `dag`）

两种方案都自洽，但不能同时作为"当前生效方案"——如果按 v2.1 的 DAG-only 口径开发采集层，那么现有的 `workflow_graph_schema_v2.json` 和样例数据就需要同步修订（把 `loop_back` 边改写成 `retry_semantics`）；如果保留 `loop_back` 边，则 v2.1 文档里"主 DAG 不含环"的一系列 Validator 规则（第17节"新增 Edge 后不得形成 cycle"）需要放宽为"仅在特定 `graph_type` 下要求无环"。

**建议**：采用 v2.1（DAG-only + retry_semantics）作为本次移动/桌面采集层的唯一口径——原因是它能保证图始终可拓扑排序，便于移动端"自动布局 + 自动居中"这类依赖 DAG 层级结构的渲染逻辑稳定工作；但这意味着 `schema/` 目录下两份文件需要在正式开发前由你确认是否同步更新。本 PRD 暂不擅自修改 schema 文件，留待你确认。

### 7.2 节点类型集合的差异

v2.1 的 MVP 节点集合比更早版本少了 `event`、`subprocess`（v2.1 第10节标注为"后续可扩展"），而 `schema/workflow_graph_schema_v2.json` 已经把两者列为正式支持类型。若按 v2.1 做 Phase A/B 的 MVP，需要明确：Schema 里已经存在但产品暂不采集的字段，是保留在 Schema 里"允许但本期不产出"，还是本期就直接支持。建议保留在 Schema 里但采集 UI 暂不引导专家产出，两者不冲突，只是需要在 Graph Validator 里确认不会因为"缺失 `event`/`subprocess` 相关字段"而报错。

## 8. 验收标准（在桌面端已有标准基础上补充移动端条目）

### 8.1 专家体验（桌面 + 移动共用）

- 不出现强制 DAG/BPMN 术语
- 专家可以只用自然语言（含语音）完成采集
- 分支、并行、汇合能被正确追问
- 图形界面专家能看懂（移动端额外要求：默认缩放级别下一眼看清全貌）
- 专家可以纠错（移动端：纠错入口收敛在会话页，DAG页有明确的"回会话说"引导文案）

### 8.2 移动端专项验收

- [ ] 主页默认展示会话页，非历史列表页
- [ ] 左上角列表图标点击后正确弹出历史流程抽屉，且抽屉内容与桌面端左栏字段一致（名称/行业/场景/状态/完成度/更新时间）
- [ ] 非边缘区域右滑正确切换到 DAG 页，边缘 20px 区域内起始的滑动不触发页面切换（不与浏览器返回手势冲突，需在 iOS Safari、Chrome Android 上实测）
- [ ] DAG 页支持双指缩放、单指平移，首次进入自动适配全图
- [ ] DAG 页所有交互均为只读，不出现任何编辑入口
- [ ] 语音口述转文字的取消/停止/发送三个状态按钮在移动端触控下正常工作，且识别文本正确进入采集轮次
- [ ] 语音输入过程中，左右滑动切换页面的手势被临时禁用
- [ ] 同一账号在桌面端和移动浏览器间切换，能看到同一会话的最新状态（DAG、完成度、待确认项一致）

### 8.3 数据与 AI（复用第3.3、3.4节标准，不因移动端而降低要求）

- 输出是合法 DAG，可拓扑排序（若第7.1节确认沿用 v2.1 口径）
- 所有自动抽取都有 `source_turn_ids` 证据
- AI 不静默补写事实、不静默解决冲突

## 9. 里程碑建议

在桌面端已有的 Phase A/B/C（`design/conversational_collection_design.md` 第34节）基础上，追加移动端阶段：

| 阶段 | 内容 |
|---|---|
| Phase A（桌面，沿用原计划） | 三栏界面、历史流程、会话、DAG节点/边/分支/并行/汇合、实时右栏图、Validator、专家确认 |
| Phase B（桌面，沿用原计划） | 规则/经验、Artifact、交接、审批、返工语义、会话冲突处理 |
| **Phase M1（移动，新增）** | 会话页（文字输入）+ 历史抽屉 + DAG只读页（缩放平移，不含语音） —— 先跑通移动端的两页导航与只读图渲染 |
| **Phase M2（移动，新增）** | 接入语音口述转文字（取消/停止/发送三态），完成 8.2 节验收 |
| **Phase M3（移动，可选增强）** | "实时语音对话"连续追问模式（4.3.1 表格中的第三种输入方式） |
| Phase C（沿用原计划） | 自动质量评估、Gold Annotation、多专家复核、数据集版本、实验直接联动 |

建议 Phase M1/M2 在桌面 Phase A 基本稳定（DAG 数据模型、Graph Ops、Validator 已跑通）之后再启动，因为移动端复用的是同一套后端和数据模型，先在桌面端把模型跑稳可以避免移动端返工。

## 11. DAG 可视化重新设计（桌面 + 移动通用视觉语言）

### 11.1 定位：原型仅供参考，本节是新的视觉规范

`design/conversational_expert_collection.html`、`design/manufacturing_expert_workflow_collection_v2.html` 里的 DAG 展示（简单的绝对定位节点 + 直线连线，`.dag` 容器手写坐标）只是**验证信息结构够不够用**的草图，不是视觉终稿——手写坐标无法应对真实专家流程的节点数量和分支复杂度，颜色和间距也偏工程感。本产品的核心用户是**制造一线专家，不是算法/产品同事**，DAG 图是他们唯一要"读懂并纠错"的界面，美观直观的优先级不低于功能正确性。本节给出替代方案，第 12～14 节的其他页面如涉及图表，也遵循这里定的视觉基调（克制、留白、语义化颜色），不单独另定一套。

### 11.2 设计原则

1. **一眼看懂结构，不需要图例也能猜个大概**：起点/终点用胶囊形状+柔和灰底一眼区分于"事情"；判断用菱形或圆角矩形+暖黄区分；并行/汇合用有方向性的图形提示（左右对称的分叉/汇入形状），不是靠专家去记颜色对照表
2. **颜色只做语义分类，不做装饰**：一种结构类型固定一种色相（活动=中性灰/蓝、判断=琥珀、并行=紫、汇合=靛蓝、审批=绿、起止=更浅的灰），同一色相的浅底+深描边用于默认态，选中态整体加深，不引入额外的强调色系统
3. **自动布局，专家不用摆位置**：分层有向图（ELK.js `layered` 算法），主干在一条水平/垂直基线上，分支和并行结构在基线两侧展开，避免连线交叉——这是"美观"里权重最高的一条，连线交叉是专家看不懂图的头号原因
4. **渐进呈现，先见森林后见树木**：默认缩放级别只显示节点形状+极短标签（4~6字），聚焦/放大后才显示完整描述、角色、规则引用——避免小屏幕或整体缩略图时文字糊成一团（呼应第 4.4.1 节移动端要求，桌面端同样适用）
5. **不做 BPMN 重型图标**：不用泳道（swimlane）、不用信号/消息/定时器等 BPMN 专业符号，这些术语专家不认识；角色信息用节点内一行小字（"质量工程师"）而不是泳道分栏

### 11.3 视觉规范（供前端直接取用的具体数值）

| 节点类型 | 形状 | 填充色 | 描边色 | 图标 |
|---|---|---|---|---|
| `start` / `end` | 圆角胶囊 | `#F8FAFC`（近白） | `#94A3B8` | 空心圆点 |
| `activity` | 圆角矩形（8px） | `#FFFFFF` | `#CBD5E1` | 无（默认态） |
| `decision` | 菱形圆角 | `#FFFBEB` | `#F59E0B` | 问号 |
| `parallel_split` / `parallel_join` | 六边形 | `#F5F3FF` | `#8B5CF6` | 分叉/汇入箭头 |
| `merge` | 圆角矩形+左侧竖条 | `#EFF6FF` | `#3B82F6` | 汇入箭头 |
| `approval` | 圆角矩形+右上角徽标 | `#ECFDF5` | `#10B981` | 对勾徽标 |
| `handoff` | 圆角矩形+虚线右边框 | `#FFFFFF` | `#CBD5E1`（虚线部分 `#F97316`） | 交接图标（两个箭头） |

- 边（Edge）：默认 1.5px 实线 `#94A3B8`，条件边（`conditional`）额外带一个浮动小标签（白底+细描边，显示条件文字，如"复测正常"），不用箭头颜色区分条件——颜色留给节点类型专用
- 字体：系统默认无衬线字体（`-apple-system, "PingFang SC", "Microsoft YaHei"` 兜底），节点主标签 13–14px 加粗，副标签（角色/系统）11px 常规灰色
- 间距：同层节点间距 ≥ 32px，层间距 ≥ 64px（分支展开后视觉上不拥挤）
- 圆角统一 8–10px（六边形/菱形除外），阴影极轻（`0 1px 3px rgba(0,0,0,.06)`），不用重投影制造"卡片悬浮"的厚重感

### 11.4 交互层

- **默认自动布局 + 自动适配画布**：图更新后重新跑一次 ELK 布局，但保留专家手动拖动过的节点位置（`manual_position`，`design/conversational_collection_design.md` 第31节已有此设计，本节沿用），避免图跳动过大打断阅读
- **Hover/点击高亮路径**：桌面端 hover 一个节点，高亮它的直接上下游边和节点，其余淡化（不删除，只降低不透明度到 40%），帮助专家在复杂图里定位"这一步之前/之后是什么"
- **图例常驻但极简**：桌面右栏图下方一行小图例（形状+色块+一个词），不用弹窗解释，移动端收进"检查流程"入口里
- **详情展示**：桌面点节点在右侧/下方展开详情面板；移动端用底部半屏卡片（4.4.1 节已定），两端内容结构一致（自然语言描述、角色、关联规则/经验判断）

### 11.5 参考实现

已按以上规范产出一份可直接在浏览器打开预览的重设计原型：[`design/dag-view-redesign.html`](design/dag-view-redesign.html)（同一张 CNC 尺寸超差处理案例图，对照 `design/conversational_expert_collection.html` 原版可以直接看出视觉差异）。这份文件是**设计目标参考**，不是最终前端实现——真实前端仍按 6.1 节的 React Flow + ELK.js 技术方案构建，样式规范取自本节的 11.3 表格。

### 12.1 页面结构

沿用已有设计的六个 Tab（`design/manufacturing_workflow_platform_design_v2.md` 第16节）：

| Tab | 内容 |
|---|---|
| 数据集列表 | `public_extracted` / `expert_collected` 两类分开展示，每个数据集显示名称/类型/版本/样本数/Graph类型分布/Gold比例/Dataset Readiness/更新时间/推荐用途 |

### 12.2 导入设计

#### 12.2.1 流程

```
上传 JSON → 预检（不直接入库）→ 预检报告 → 用户确认 → 正式导入
```

预检顺序（合并 `dataset_design_spec.md` 与 `manufacturing_workflow_platform_design_v2.md` 第19节，去重后的完整清单）：

1. JSON Schema 校验（对照 `schema/workflow_graph_schema_v2.json`，见第 7 节口径确认后的版本）
2. `source_type` 一致性检查（`dataset_meta.source_type` 与每条 `provenance.source_type` 是否一致）
3. 必填字段完整度检查
4. 制造模式/行业/流程类型合法值检查（`manufacturing_context`/`scenario` 枚举值）
5. Graph Validator（第 3.3/3.4 节同一套规则：node/edge 唯一性、start/end 合法性、decision 出口数、parallel_split/join 完整性、孤立节点等）
6. record_id 重复检查
7. 近重复流程检查（结构相似度 + 文本相似度，见 12.2.2）
8. 实体角色完整度检查
9. Gold 标注可用性检查
10. 自动生成数据集评估（调用第 13 节的八维 + Graph 质量评分逻辑，产出本次导入批次的预览分数，不写入正式 Dashboard）

#### 12.2.2 近重复检测怎么做（原设计未展开，这次补全）

两层检测，都是规则/统计方法，**不需要 LLM**：

- **文本层**：记录的 `scenario.trigger` + 节点 `label` 拼接后的 TF-IDF/MinHash 相似度，超过阈值（建议 0.85）标记为疑似近重复
- **结构层**：Graph Edit Distance（复用第 14 节实验指标里已有的图编辑距离算法）低于阈值 + 节点数/边数接近，标记为疑似同模板改写

两层任一命中都标"警告"级别，不阻断导入，交给用户在预检报告里决定是否仍要导入。

#### 12.2.3 预检报告

至少显示（沿用两份原设计文档已列的完整清单）：总记录数、可导入记录数、阻断错误数、警告数、Coverage/Balance/Completeness/Extractability/Authenticity/Annotation Readiness/Diversity/Leakage Risk 八维分数、Graph 结构分布（Linear/DAG/Directed Graph 比例、平均节点数/边数/分支数/并行结构数）、Dataset Readiness Score，以及系统给出的用途建议（可用于主实验 / 适合辅助实验 / 需人工复核 / 不建议使用）。只有用户点"确认导入"后才正式入库。

### 12.3 导出设计

- 范围：整个数据集 / 当前筛选结果 / 指定记录
- 格式：`raw`（原始版）/ `anonymized`（匿名版，需要设计一版专家个人信息脱敏规则，见 12.4）/ `role_normalized`（角色归一化版，把"质量工程师""QE""质检"统一映射成标准角色名）
- 可选是否包含 Gold Annotation
- 可按 `source_type`/行业/制造模式/流程类型/`graph_type`/标注状态/推荐用途筛选
- **导出文件必须保留** `dataset_meta.source_type` 和每条记录 `provenance.source_type`（两份原设计都强调这条，避免外部系统回传后丢失来源属性——沿用不变）

### 12.4 匿名化规则（原设计未展开，这次补全）

导出 `anonymized` 版本时，至少做：

- `provenance.expert_id_hash` 保留哈希、去掉可反推真实身份的 `expert_role`+`expert_years_experience` 组合中的极端值（例如"唯一一位有35年经验的退休返聘专家"这种描述性极强的字段建议分桶处理，如"30年以上"）
- 节点/规则/经验判断里如果专家口述时提到了具体姓名（"李工""张主管"），需要在会话阶段或导出阶段做人名脱敏——**这一步需要 LLM 辅助**（识别自然语言文本里的人名指代并替换成角色代称），规则式脱敏（正则匹配姓氏词典）召回率不够，详见第 15 节清单
- `role_normalized` 版本本身也依赖 LLM/规则混合做角色名归一化，见第 15 节

## 13. Dashboard 完整设计

**访问范围**：仅桌面浏览器端；仅"研究员""管理员"角色可见（角色定义见第 16.2 节），专家账号登录后看不到这个入口——这条审查时补上，原设计文档只在权限章节提过角色划分，没有落到具体页面的可见性规则上。

### 13.1 定位与原则

沿用两份原设计文档的核心主张（`design/dataset_design_spec.md` 第二节、`design/manufacturing_workflow_platform_design_v2.md` 第22~26节）：**重点不是"有多少数据"，而是"这批数据是否足以支撑公平、可复现的实验"**。默认区分专家集/公共集，一键切换，不混合统计。

### 13.1.1 页面结构（原设计缺失，本轮补上）

两份原设计文档都只列了"要显示什么指标"，没有说"这些指标怎么组织成一个可以导航的页面"，审查时发现这是实际能不能做出来的关键缺口。补充为三段式纵向结构，桌面单栏滚动（Dashboard 本身信息密度高，不适合再切三栏）：

```
┌───────────────────────────────────────────────────────────┐
│  Dashboard              [专家集 ●┃○ 公共集]   最近更新: 3分钟前 │
├───────────────────────────────────────────────────────────┤
│  一级指标卡片行（13.2）                                       │
├───────────────────────────────────────────────────────────┤
│  [质量评分] [完整度明细] [泄漏与重复] [趋势]  ← 二级 Tab        │
│  当前 Tab 的内容（13.3～13.4）                                │
└───────────────────────────────────────────────────────────┘
```

- 顶部专家集/公共集切换用 segmented control（不用下拉），因为这是整个页面最高频的操作，两类数据"一键切换、不混合统计"的硬性要求（13.1）需要一个足够显眼的控件来承载
- 二级 Tab 里新增一个原设计没有的**"趋势"**页：数据集规模、Readiness Score、各维度分数随时间（周/月粒度）的折线走势——两份原设计都提到"最近新增"这类瞬时值，但没有任何随时间变化的视图，而"数据集质量是不是在变好"本身就是研究员会关心的问题
- 页面右上角固定显示"最近更新"时间戳——Dashboard 的数字不是实时的（见 13.6 计算方式，多数是批处理统计），必须让用户知道这是哪个时间点的快照，避免误以为是实时数据

### 13.2 一级指标（顶部卡片）

数据集数、Workflow 数、步骤总数、微工作流识别数、专家数、公共来源数、Gold 数量、近重复风险、最近新增、待复核。相比 v0.3 做了两处调整（用户反馈后修订）：

- **去掉了顶部卡片里的 Dataset Readiness**：这个分数在 13.3 节"质量评分"Tab 里已经是整个 Tab 的主角（大号数字 + 状态徽章），顶部卡片再放一次纯属重复，两处一旦某次更新不同步还会互相矛盾，直接删除顶部这一份，只保留一个权威位置
- **新增"步骤总数"**：所有已采集 Workflow 的节点总数之和，衡量数据集的"体量"而不只是"有多少条 Workflow"——两条 Workflow 数一样多的数据集，步骤总数可能差好几倍，这是研究员评估数据规模时的常见追问
- **新增"微工作流识别数"**：跨 Workflow 复用的可复用子图（reusable operational subgraph，概念见 `legacy-prototype/TWO_STAGE_PAPER_STRUCTURE_DAG.md`）数量——这是本产品区别于"只是存了一堆流程记录"的核心研究价值指标：数据集里到底沉淀出了多少可复用的组织经验模式，而不是一堆各自独立的孤立案例。识别算法是结构化子图挖掘（`consensus_dependency_graph`/`graph_semantic` 一类的图挖掘方法，legacy-prototype 已有原型实现），**不需要 LLM**

**每一项都要有 tips 图标**（沿用 `design/conversational_expert_collection.html`/`dag-view-redesign.html` 里已经在用的 `.tip-icon` 悬浮提示模式）：鼠标悬停/点击显示这个指标具体怎么算、口径是什么，例如"微工作流识别数"的 tips 要说明"跨 3 条及以上 Workflow 复用、结构相似度超过阈值的子图才计入，一次性出现的独特流程不算"。这条本次修订前遗漏了——顶部卡片信息密度高，字面标题容易产生歧义（比如"Workflow 数"和"步骤总数"不加说明容易被读反）。

### 13.3 数据集质量评价：完整的十维评分体系

这是本节的核心，也是你这次特别点名要完整设计的部分。合并 `dataset_design_spec.md` 的八维通用评估 + `manufacturing_workflow_platform_design_v2.md` 第25节的 Graph 专用质量指标，形成完整的 **Dataset Readiness Score v2**：

| 维度 | 权重 | 具体子指标 |
|---|---:|---|
| 覆盖度 Coverage | 15% | 制造模式覆盖率、垂直行业覆盖率、场景类型覆盖率、四类流程类型覆盖率、岗位覆盖率、系统/设备对象覆盖率 |
| 平衡度 Balance | 10% | 各制造模式/行业/流程类型样本偏斜度、单一专家贡献占比、单一来源/企业占比 |
| 流程完整度 Completeness | 15% | 平均步骤数、≥5步样本比例、有明确触发/结束条件比例、有角色/系统信息比例、有关键判断节点比例 |
| Graph 结构完整度 Graph Completeness | 15% | 有明确 start/end 比例、decision 条件完整率、parallel_join 完整率、`retry_semantics` 条件完整率（对应第 7.1 节口径）、孤立节点比例（应为 0） |
| 可抽取性 Extractability | 10% | 步骤顺序明确率、单步动作清晰率、角色-动作可对应率、判断条件可解析率、模糊词/省略词比例、重复/空步骤比例 |
| 真实性与来源可信度 Authenticity | 10% | 专家集：岗位已知率、经验年限已知率、真实案例确认率、人工复核比例；公共集：来源可追溯率、一手来源比例、原文引用完整率 |
| 标注成熟度 Annotation Readiness | 10% | Gold Boundary/Role/Edge/Node 覆盖率、双人标注比例、已仲裁比例、标注一致性（Cohen's Kappa / Boundary F1 Agreement） |
| 多样性 Diversity | 5% | 专家数量、岗位数量、流程长度分布、协作人数分布、系统组合数量、决策分支复杂度 |
| 结构多样性 Structural Diversity | 5% | Linear/DAG/Directed Graph 比例、含分支/并行/回路/异常路径比例——避免数据集被采成"全是简单线性流程"（呼应 `design/conversational_collection_design.md` 第29节 Dashboard 设计初衷） |
| 低泄漏风险 Low Leakage Risk | 5% | 近重复流程比例、同模板改写比例、Train/Test 高相似样本数量、同一专家跨训练/测试泄漏风险 |

**总分只是概览，Dashboard 必须同时展示全部原始子指标**，不能只给一个数字——两份原设计都反复强调这条，本次保留为硬性要求。

### 13.3.1 每个评分项的解释弹窗（用户反馈后新增）

质量评分 Tab 里的十个维度，每一项默认只显示一个分数和一条进度条，研究员看到"结构多样性 61 分"并不知道 61 分具体是怎么算出来的、这个数据集当前是因为什么被扣分。补充设计：**每个维度行都可以点开一个解释弹窗**，内容分两段：

1. **评分标准**：这个维度满分/中间/低分档位分别对应什么情况，用固定文本（针对维度写死，跟具体数据集无关，例如"结构多样性：Linear 类型占比越高、含分支/并行/回路的比例越低，分数越低；80分以上要求至少三种结构类型均有覆盖"）
2. **当前分数的依据**：针对*这个数据集当前这次评分*的具体解释——用富文本（加粗关键数字、列表），并且**举出 1～2 条具体样本作为例子**（例如"当前 61 分主要是因为：现有 128 条 Workflow 里 Linear 类型占 61%（如《SMT首件确认》《ECN导入量产》），含并行结构的只有 18%，含回路/返工语义的只有 9%"），不是泛泛的"分数偏低"

**生成时机**：跟评分本身**同一批次生成，不是用户点开弹窗时才现算**——评分是批处理任务（见 13.6 节），"当前分数依据"这段解释文字在那次批处理里一起生成好、存下来，用户点开弹窗只是读取已经生成的内容，不会有等待。评分标准这段是纯静态文案，不随数据变化，每个维度写一次即可。

### 13.4 详情下钻

- 点击任意维度分数 → 展开该维度的子指标明细图表
- 点击"定位问题样本" → 直接筛出拖低该维度分数的具体记录（例如"孤立节点比例"分数低，点击后列出所有含孤立节点的记录，可以直接跳转到该记录的 Graph 详情去看是哪个节点）——这是"能定位具体问题样本"这一验收标准（原设计第37节）的具体落地方式
- 完整度明细表、泄漏与重复检查表（沿用 `manufacturing_expert_workflow_collection_v2.html` 原型里已有的两张表格样式）

### 13.5 可视化设计要点

Dashboard 大量使用条形进度条（分数条）、表格、少量趋势折线图。遵循第 11.2 节的克制原则，并按"量级用单一顺序色、状态用固定状态色、多序列比较才用分类色"这条统一规则分工，三者不混用：

- **十维评分条形图**：magnitude（数值大小）用**单一顺序色**（蓝，浅→深），不为每个维度分配不同颜色——八/十个维度同时出现时过多颜色会干扰"哪个分数低"这个核心问题的识别，只用条长本身传达信息。横向条形图并排展示，不用雷达图（维度多、量纲一致时雷达图确实直观，但对色弱用户和小尺寸屏幕不友好，横向条形图在打印场景也更稳）
- **总分/单项分数的"好坏"判断**：用固定的状态色（好/警告/较差/差），不复用条形图的顺序蓝色——例如 Dataset Readiness Score ≥ 80 显示为"好"状态色，60~79 为"警告"，< 60 为"较差"，这样用户扫一眼卡片颜色就知道要不要点进去看，不需要先读数字再心算判断；状态色必须配图标+文字（"良好"/"待改善"），不能只靠颜色，兼顾色弱用户
- **专家集 vs 公共集对比**（新增的"趋势"Tab 如果叠加显示两类数据的同一维度走势）：这才是真正的多序列比较，用分类色的前两个色相（区分身份，不代表大小），并保证图例常驻、不靠颜色单独区分
- **趋势折线图**：单一指标随时间变化用一条线（顺序蓝或对应的分类色），横轴统一到"周"粒度，避免数据点过密

### 13.5.1 缺数据/小样本状态（审查时发现原设计遗漏）

新数据集或专家集刚起步时，多数维度分母很小（比如只有 3 条专家记录），此时算出来的比例类指标（如"Balance"）容易剧烈波动、参考意义低。规则：样本数低于一个阈值（建议 20 条）时，对应维度分数区域显示"样本量不足，暂不评分"而不是硬算出一个误导性的数字，避免团队因为早期一个虚高或虚低的分数做出错误判断。

### 13.6 计算方式：全部是确定性统计，不需要 LLM

需要特别说明：**第 13.3 节的十维评分体系里，绝大多数子指标是可以纯规则/统计计算的**（比例、计数、分布、Kappa 系数等），不需要调用 LLM——这是"用户端可解释、可复现"的重要前提，如果分数本身依赖 LLM 判断，就会引入不可控的波动。少数需要语义判断的子指标（如"模糊词/省略词比例"里判断某个描述是否算"模糊"）建议用规则词典（一批"待确认""可能""大概"之类的高频模糊表达）而不是 LLM 分类，同样出于可复现性考虑。

**例外**：**分数本身**（数字）永远是规则计算的，但 13.3.1 节新增的"当前分数依据"这段解释文字**需要 LLM**——把规则算出来的统计结果（比例、计数、命中的具体样本）转成一段人话解释，属于"表达"不属于"判断"，不影响分数的可复现性（同样的统计输入，用固定模板也能拼出一版能读的文字，LLM 只是让它读起来更自然、能自动挑出合适的举例样本）。这条已经在第 15 节 LLM 清单里补上。

### 14.5 新增：实验结果的详细文字解释（本轮新增需求）

原设计的结果页只有指标表格和图表，对不熟悉这些指标定义的人（产品经理、专家本人、甚至算法同事临时切换到不熟悉的实验类型时）不够友好。本次新增一个**"结果解读"卡片**，放在 Summary 层的最上方：

#### 14.5.1 内容结构

一段总览（100–200字，直接说结论："本次实验在主干节点识别上表现良好（Node F1 0.89），但在条件分支的识别上偏弱（Branch Condition Accuracy 0.61），最常见的错误是把多条件分支漏识别成两条件"）+ 分点列表（3–5条，每条对应一个维度的具体解读，格式统一为"**现象** → **可能原因** → **建议**"）。

#### 14.5.2 解读怎么生成：LLM，但受控输入，不是让模型自由发挥

- **输入严格限定为结构化数据**：本次实验的全部指标数值、（如有）对照实验/baseline 的同一批指标、Error Analysis 层已经聚类好的典型错误案例摘要（不是全部原始记录，避免超长上下文和信息过载）——不给模型任何本 PRD 之外的背景假设
- **Prompt 明确要求**：只基于给定的数字和案例做解读，不允许编造没有数据支撑的结论；每条解读必须落到具体维度和具体数字，禁止"整体表现不错"这类空泛套话；文字风格面向非算法背景的读者，避免堆砌指标术语而不解释
- **必须提示"这是自动生成的摘要"**：解读卡片下方固定一行小字"以上解读由 AI 根据本次实验指标自动生成，请结合下方明细数据核实"，不能让用户误以为是人工撰写的正式结论
- **可重新生成、可编辑**：研究人员对生成的解读不满意时可以点"重新生成"，或者直接编辑后保存（编辑后的版本标记为"已人工修订"，不会被下次重新生成覆盖）
- **生成时机**：实验 Run 完成、所有指标计算完毕后触发一次，不在实验运行过程中生成（不是关键延迟路径，可以等 5-10 秒）；也支持事后对已完成的实验手动触发生成

#### 14.5.3 Error Analysis 层的典型案例聚类（同样建议用 LLM，作为 14.5.2 的输入准备步骤）

原设计的 Error Analysis 层只说"典型失败案例"，没说案例从哪来、怎么归类。建议：数量较多的失败案例先用规则/统计做初步分组（比如按"哪个 Graph 结构类型出错"分组），组内数量仍然很大时，用 LLM 对组内案例做二次归纳，提炼出 2–4 种"典型失败模式"的描述（而不是要求人工翻看几十条案例各自的原始输出），这个归纳结果同时也是 14.5.2 解读卡片的输入之一。

### 14.6 实验对比（原设计缺失，本轮补上）

两份原设计文档都只设计了"单个实验的结果页"，完全没有设计"多个实验放在一起比"这个研究员最常见的实际需求（换了个 baseline 方法/换了个模型，效果有没有变好）。补充设计：

- 从 14.1.1 的实验列表勾选 2～5 个**已完成**的实验（超过 5 个不允许同时对比，避免图表挤成一团难以辨认）
- 对比视图三段：
  1. **指标对比表**：行是 14.3 列出的全部指标，列是被选中的实验，每行标出最优值（不是简单加粗最大数字，需要先判断该指标"越高越好"还是"越低越好"，例如 Graph Edit Distance 是越低越好）
  2. **对比条形图**：挑选 Node F1 / Edge F1 / Branch Condition Accuracy / Graph Structural F1 四个最核心的指标，每个指标一组并排条形，不同实验用分类色区分（复用 13.5 节确立的"多序列比较用分类色"规则，同一个实验在整个对比视图里固定同一个颜色）
  3. **对比解读**（复用 14.5.2 的 LLM 解读机制，输入换成多个实验的指标差异而不是单个实验的指标本身）：例如"实验B相比实验A（baseline），Branch Condition Accuracy 从 0.61 提升到 0.78，提升主要来自...；但 Graph Edit Distance 略有上升，说明..."
- 对比视图里的每个实验名称都可点击跳转回它自己的单实验结果页（14.4），对比视图是导航枢纽，不是终点

### 14.7 参考实现

按 14.0～14.6 节的页面结构、结果解读卡片、对比视图产出了一份可交互的参考原型：[`design/experiment-center-redesign.html`](design/experiment-center-redesign.html)（含实验列表、单实验结果页、多实验对比三个视图切换）。数据是虚构的示例。

## 15. 本产品需要 LLM 的环节清单

直接回答你的问题：以下是本产品（专家采集 + 数据集 + Dashboard + 实验中心）里**明确需要 LLM** 的环节，按是否在关键交互延迟路径上分组。所有环节都遵循第 4.7 节确立的边界——**不联网检索，只基于会话/实验/数据集自身内容做处理**。

### 15.1 关键路径（用户等着看结果，需要低延迟）

| 环节 | 用途 | 对应章节 | 建议模型量级 |
|---|---|---|---|
| 专家采集会话引导 | 复述、澄清、生成下一条追问、把自然语言转成 Graph Ops（结构化抽取） | 第 3.2、3.3 节 | 7B 级别（原设计定位），需要低延迟和稳定的结构化输出（JSON） |
| 移动端语音口述整理（可选） | 把 ASR 原始转写整理成书面语（是否需要取决于实测转写质量，见 6.2 节） | 第 6.2 节 | 轻量模型（`qwen-turbo` 级别），一次性调用 |

### 15.2 非关键路径（异步/事后生成，可以用更强模型、容忍数秒延迟）

| 环节 | 用途 | 对应章节 | 建议模型量级 |
|---|---|---|---|
| 实验结果文字解读 | 把量化指标 + 典型错误案例转成面向人的自然语言解读 | 第 14.5.2 节 | 更强的模型（`qwen-plus`/`qwen-max` 级别均可，非延迟敏感） |
| 多实验对比解读 | 把多个实验的指标差异转成"谁比谁好在哪、可能为什么"的解读 | 第 14.6 节 | 同上，输入是差异数据而非单实验指标 |
| Dashboard 评分项"当前分数依据"解释 | 把每个质量维度的统计结果（比例/计数/命中样本）转成带举例的解释文字，随批量评分任务一起生成、缓存下来 | 第 13.3.1 节 | 中等模型即可，输入是已经算好的统计数字，不需要模型自己判断分数 |
| Error Analysis 案例聚类归纳 | 把大量失败案例归纳成几种典型失败模式 | 第 14.5.3 节 | 中等模型即可，输入是已经过规则初筛的案例摘要 |
| 导出匿名化：人名脱敏 | 识别专家口述/记录文本里的人名指代并替换成角色代称 | 第 12.4 节 | 轻量模型或规则+LLM混合，命中率要求高于速度要求 |
| 角色归一化（role_normalized 导出） | 把"质量工程师""QE""质检"等同义表达映射到标准角色名 | 第 12.4 节 | 轻量模型，可配合一份人工维护的同义词典兜底 |

### 15.3 明确不需要 LLM 的环节（容易被误以为需要，特此说明）

- **数据集质量评分（第 13.3 节十维体系）**：全部是确定性统计计算，不调用 LLM，保证分数可复现、可解释
- **Graph Validator**（第 3.3、3.4、12.2.1 节）：结构合法性校验是纯规则逻辑（唯一性、连通性、出入度要求等），不需要语义理解
- **近重复检测**（第 12.2.2 节）：文本相似度 + 结构相似度算法，不需要 LLM
- **完成度 Completion Score**（第 3.5 节）：按固定权重公式计算，不需要 LLM

原设计文档只在"权限"章节（`manufacturing_workflow_platform_design_v2.md` 第34节）列了三种角色的权限清单，从未设计成一个真正的页面。第 1.4 节已经把管理页面列为桌面端四大功能模块之一，这里补上最小可用的页面设计。

### 16.1 页面结构

```
管理页面
├─ 用户与权限：账号列表、角色分配（专家/研究员/管理员）
├─ 数据集发布：把某个数据集版本标记为正式发布 / Gold 版本
├─ 删除与归档：草稿删除、数据集归档（软删除，保留审计痕迹）
└─ 审计日志：谁在什么时候改了哪个节点/边/数据集/实验配置（原设计第35节"审计"要求的直接落地）
```

### 16.2 角色与权限（沿用原设计，正式收编）

| 角色 | 权限 |
|---|---|
| 专家 | 创建/修改自己的草稿，查看自己的历史流程，提交（修改已提交流程会生成新版本），**看不到** Dashboard/实验中心/管理页面入口 |
| 研究员 | 查看数据集，导入导出，Dashboard，创建/运行/对比实验，标注 |
| 管理员 | 以上全部 + 用户与权限管理、数据集发布、Gold 版本标记、删除/归档 |

### 16.3 审计日志的最小字段

沿用原设计（第35节）要求：谁修改了哪个节点/边、修改前后的值、是 LLM 自动修改还是人工修改、谁确认、谁标注 Gold、哪个实验用了哪个版本数据——这批字段是实验可复现性（14.1.1 节）和数据可信度的基础，管理页面的审计日志视图只是把这些已经在写的记录做成可查询的列表，不需要额外设计新的数据结构。

### 16.4 这个环节不需要 LLM

管理页面全部是 CRUD 和权限判断，不涉及任何语义理解，不在第 15 节清单里。
