# 数据采集升级草稿：Scenario/Case Context 采集 + Prior 标注流程

> 状态：**思考初稿，未实现，未定稿**。按用户要求先把设计思路记录下来，后续再继续细化和开发。
> 位置说明：本文件对应现有产品 `expert-collection/`（PRD.md + IMPLEMENTATION_PLAN.md 所描述的系统）的两处扩展，写在 `docs/expert-workflow-collection/design/` 下，与已有的 `conversational_collection_design.md`、`dataset_design_spec.md` 并列。尚未提交 git，仅作为本地草稿。

## 0. 两个改动分别解决什么问题，以及它们和实验设计/论文的关系

现有系统的数据集有两种来源（`models.py` 里的 `SourceType = Literal["expert_collected", "public_extracted"]`）：专家从头对话式采集，以及公共集导入。这次的两个改动分别加深这两条线：

1. **给 `public_extracted`（以及未来可能出现的"大模型整合出来的"工作流）加一层专家标注**，把它从"未经检验的候选数据"变成"专家确认过的先验数据"。这正好对应我们之前修订实验设计文档里 §4.7A Experiment 0 所需要的 \(\pi_{proc}\) / \(\pi_{ont}\) 这类"先验知识"来源——现在这些先验大多是研究者手工构造的，而 Expert-annotated Prior 标注流程可以让它们变成**真实、可追溯、有专家背书**的先验，同时也是论文 §4.18 Real AgentNexus Validation 里"专家标注 episode 边界/操作意图/是否有意义/是否可复用"这套标注体系在产品里的落地。
2. **给 `expert_collected` 的对话式采集流程，在正式画图之前加一段结构化的"情境/背景"采集**，直接对应论文里反复出现的三个概念：
   - **Scenario**（发生了什么、为什么要处理、目标是什么、成功状态是什么）——对应实验设计 §4.3 里每个 micro-workflow 的"触发场景"，以及 §4.14 半合成验证给 agent 的那种情境描述（"Line 3 has stopped unexpectedly...")；
   - **Case Context / Environment**（已知信息、未知信息、限制、可求助的人、可用资源）——这是目前系统完全没有采集的一层，但正是论文里"manufacturing operational work"定义中"interpret operational events"这一步的原始材料；
   - 后续对话本身（第一步做什么、中途判断变化、是否求助、是否审批、如何判断结束）——这部分和现有 FSM 的 `branch_check` / `approval_check` / `retry_check` / `end_condition` 是重叠的，不需要重新设计，只需要把"为什么这样做"这类归因型追问补进已有 stage。

两个改动互相独立，可以分别排期，但共享同一个理念：**让采集到的每一条数据，不管是专家写的还是导入的，都带上"这条数据为什么值得信"的证据**，而不只是一张流程图。

## 1. 修改二（优先设计，改动更贴近现有 FSM）：Expert-authored 流程的 Scenario / Case Context 采集

### 1.1 现状

看了 `guide_service.py` 现在的实现：`opening` 阶段只给 4 个大类 chip（设备/质量异常、标准生产工作、持续改善、工程/工艺变更）+ 一句自由文本，紧接着 `trigger_detail` 阶段就直接问"当时是谁最先发现的？发现后第一件事做什么？"，然后马上开始 `main_path` 画图。也就是说，专家一开口就在描述"第一步"，**"为什么处理这件事""目标是什么""当时都知道什么/不知道什么/有什么限制"这些问题现在完全没有被问到**，只是把专家说的第一句话原样存进 `pending["scenario"]` 这个字段里，从未结构化，也从未在最终数据里单独暴露出来。

### 1.2 设计目标

- 把"情境/背景"从"埋在第一句自由文本里"变成"结构化字段"，可以单独导出、单独展示、单独用于后续标注和实验里的 case context。
- 不能让专家采集流程变得冗长枯燥——现有系统已经证明"气泡chip + 少量自由文本"这种轻量交互是有效的（Phase 1/5 的 quick-reply chips），新增的情境问题必须延续这个风格，而不是变成一张表单。
- 新字段要能对应回论文里的概念，方便以后同一批数据直接喂给 §4.18 的专家标注流程或 §4.14 的半合成对照实验，不用再做一次转换。

### 1.3 问题分组

把用户列的一长串问题，按"信息类型"而不是"提问顺序"分成三组，其中第三组基本复用已有 stage，只是要求追问"为什么"：

**A组 — Scenario（触发与目标，3问，必答）**
1. 当时发生了什么？为什么需要处理这件事？（可合并成一问，因为专家通常会一起说）
2. 当时最主要的目标是什么？
3. 如果这件事处理成功，应该是什么状态？（即"成功状态"/postcondition）

**B组 — Case Context（处境，4问，建议答但可跳过）**
4. 当时你知道哪些信息？
5. 哪些信息是不知道的？
6. 当时有哪些限制？（时间/成本/安全/合规等）
7. 有哪些人可以帮忙？有哪些设备/资源可用或不可用？（这两问可以合并成一个"可用资源"问题，人和设备都算资源）

**C组 — Execution Narrative（执行过程，复用现有 FSM，只是要求追问归因）**
8. 你第一步做了什么？为什么这样做？→ 对应现有 `trigger_detail`/`main_path`，只需要在每次记录一个节点后，追加一句可选追问"为什么这样做"，存成节点的 `rationale` 字段，而不是新增 stage；
9. 中途有没有改变判断？→ 对应现有 `branch_check`；
10. 有没有向别人求助？→ 对应现有 `parallel_check`/协作节点；
11. 有没有人工审批？→ 对应现有 `approval_check`；
12. 最后怎么判断事情结束了？→ 对应现有 `end_condition`，同样只需追加"依据是什么"这一问。

**结论：真正需要新增的只有 A、B 两组共 7 个问题，C 组是给已有 stage 加"为什么"追问，不需要新 stage。**

### 1.4 新的 FSM 序列（草案）

```
opening (不变，选大类)
  ↓
scenario_trigger      "当时发生了什么？为什么需要处理这件事？"
  ↓
scenario_goal         "当时最主要的目标是什么？"
  ↓
scenario_success      "如果这件事处理成功，应该是什么状态？"
  ↓
context_known         "当时你知道哪些信息？"           [可跳过]
  ↓
context_unknown       "哪些信息是不知道的？"            [可跳过]
  ↓
context_constraints   "当时有哪些限制？"                [可跳过]
  ↓
context_resources     "有哪些人或设备/资源可以帮忙、可用或不可用？" [可跳过]
  ↓
trigger_detail (沿用现有实现，"当时是谁最先发现的？第一件事做什么？")
  ↓
... 现有 main_path / branch_check / ... 不变，只在关键节点追加"为什么"追问
```

A 组三问建议**不可跳过**（这是论文里 §4.3 每个 micro-workflow 定义的触发场景/目标/终止条件，是数据集里最有价值的部分，且专家通常几句话就能说清楚，采集成本低）。B 组四问建议**可跳过**（"点击跳过，直接开始描述过程"），理由：
- 已知/未知信息、限制、可用资源这几项，有些专家会觉得难以复述（尤其是"未知信息"——人很难准确回忆当时不知道什么），强制回答容易导致敷衍作答或流失；
- 但跳过要有代价提示，比如"跳过的字段会在 Dashboard 的完整度评分里体现为空白"，呼应现有 Dataset Readiness Score 的"完整度"维度，让专家有动力去答，而不是纯粹靠强制。

### 1.5 交互设计要点

- **形式延续现有气泡+自由文本混合模式**，但 B 组的四个问题建议给出 2-3 个常见选项 chip（比如 context_constraints 给"时间紧""安全风险""缺少备件""需要跨部门协调"等 chip，可多选+补充文字），降低"不知道怎么答"的门槛，这是把用户给的开放式问题转成半结构化输入的关键，纯自由文本容易变成噪音（论文里 raw representation vs semantic representation 的问题在这里同样存在）。
- **进度感**：这一段问题结束后，界面应该有一个轻量的过渡提示（"背景了解得差不多了，我们开始梳理你当时具体是怎么做的"），不要让专家觉得自己在填一张长表格。
- **移动端**：Phase 2 已经有 `MobileChatPage` + `VoiceCapsuleInput`，这部分问题应该原样复用同一套气泡/语音交互，不需要单独的移动端设计。
- 桌面端 `SessionPage` 的中栏对话流保持不变，只是多了几轮问答；右栏 DAG 视图在 A/B 组阶段应该显示"背景信息收集中，尚未开始画图"的占位状态，而不是空白 DAG，避免专家以为系统卡住。

### 1.6 数据模型草案

在 `WorkflowRecord`（`models.py`）里新增一个非图结构的字段，暂命名 `case_context`：

```json
{
  "case_context": {
    "scenario_trigger": "3号线设备突然停机，正在跑的订单是O1048...",
    "scenario_goal": "尽快恢复生产，同时不影响两个高优先级订单",
    "scenario_success": "线体恢复运行，两个高优先级订单不延期，异常原因记录在案",
    "known_info": "停机时间、报警代码、当前排产",
    "unknown_info": "停机是否会影响下游质量",
    "constraints": ["时间紧", "备件不足"],
    "constraints_note": "维修备件要从其他厂区调",
    "available_resources": "维修班组、设备工程师在场，产线B有空余产能",
    "skipped_fields": ["unknown_info"]
  }
}
```

`skipped_fields` 用于让 Dataset Readiness Score（`quality.py`）知道哪些字段是专家主动跳过的，而不是系统遗漏，避免误判为质量问题。C 组的"为什么这样做"追问，建议存成节点级别的 `rationale` 字段，加在现有 graph node 结构里，而不是塞进 `case_context`。

`case_context` 需要同步进 `schema/workflow_graph_schema_v2.json` 的导出格式，作为 `records[]` 里每条记录新增的一个可选对象，公共集导入（`import_pipeline.py`）如果本身带类似字段也可以复用同一结构，这样标注流程（见第 2 节）以后要展示 context 时,两种来源可以走同一个渲染组件。

### 1.7 对 Dashboard / Readiness Score 的影响

`quality.py` 十维度评分里目前没有专门衡量"情境完整度"的维度。这次改动之后建议在"流程完整度"维度里增加一个子指标：`case_context` 七个字段里实际填写（非跳过）的比例，加权较小，先作为诊断信息展示，不建议一上来就大幅拉低整体分数——这属于新指标要不要计入总分的产品决策，先记在这里，后面具体设计打分公式时再定。

## 2. 修改一：Prior 标注流程（Public/LLM-derived Prior → Expert-annotated Prior）

### 2.1 状态定义

建议把"先验数据"的生命周期显式建模成两个状态，而不是新增一个 `source_type`：

- **Public/LLM-derived Prior（原始态）**：现有 `public_extracted` 数据集里，通过 `import_pipeline.py` 导入的记录，或者未来"大模型整合出来的"工作流（比如把多条相似工作流用 LLM 聚合成一条候选 micro-workflow），统称为**未经专家确认**的候选数据。
- **Expert-annotated Prior（标注后）**：专家看过、逐条给出判定之后的状态。

不新增 `source_type` 的原因：`source_type` 目前用来区分数据"从哪来"（专家现场采集 vs 外部导入），而这里要区分的是"有没有被专家确认过"，是一个正交的维度。建议在 `WorkflowRecord` / dataset record 上新增一个字段 `prior_status: Literal["raw", "expert_annotated"]`，默认 `raw`，标注完成后置为 `expert_annotated`。

### 2.2 标注对象和判定粒度

一条候选工作流的图，标注时需要专家在三个粒度上给判定，但**默认只要求最粗粒度**，细粒度按需展开（用户明确要求界面"要做得容易、易用一些"，所以默认不能要求逐节点标注）：

1. **整体判定（必填，一次点击）**：`采纳` / `需要修改` / `不可用，丢弃`。这是唯一强制的操作，保证标注流程可以"秒过"一条明显没问题的记录。
2. **节点/边判定（可选，按需展开）**：只有整体判定选了"需要修改"时，才展开逐节点视图，每个节点/边给 `保留` / `删除` / `合并进上一个节点` 三个 chip，需要改文字的直接点节点内联编辑。
3. **备注（可选，自由文本）**：一句话说明为什么需要修改或丢弃，供后续排查用。

这个"默认一次点击过，需要时才展开"的设计，直接对应用户说的"标注界面要容易、易用"——大多数导入数据如果预检（`import_pipeline.py` 的十步预检）已经通过，专家标注更多是在做抽样质检，不需要逐字逐句抠。

### 2.3 界面草案

复用现有只读 `DagView` 组件展示候选图（和 Experiment Center 页面展示 consensus 图的方式一样），上方是三个大按钮（采纳/需要修改/丢弃），点"需要修改"才展开节点级操作层，操作方式参考已有 `ScoreBar` 的"点击展开 modal"交互风格，保持视觉语言一致。

标注入口建议放在 Dashboard 的"公共集"视图里（`DashboardPage.tsx` 的 `public_extracted` 分支），在 `ImportPanel` 导入确认之后，列表里每条记录旁边加一个"待标注"标签和"去标注"按钮，而不是做成一个独立页面——这样标注和导入在同一个信息流里，专家不用在多个页面之间跳转。

### 2.4 数据模型草案

新增一张 `prior_annotations` 表（对齐现有 `audit.py` 的"诚实记录"风格，不做多余抽象）：

```json
{
  "annotation_id": "...",
  "record_id": "...",
  "annotator_role": "expert",
  "verdict": "needs_revision",
  "node_verdicts": {"n1": "keep", "n2": "delete", "n3": "merge_into:n1"},
  "note": "n2 是导入时误切分出来的重复步骤",
  "annotated_at": "2026-09-20T..."
}
```

`prior_status` 在记录本身随最新一次标注结果更新；`prior_annotations` 保留全部历史，供以后做标注一致性分析（见 2.6）用。

### 2.5 对 Dashboard / Readiness Score 的影响

公共集的 Dashboard 视图应该新增一个"标注覆盖率"指标（已标注条数 / 总条数），以及"标注结果分布"（采纳 / 修改 / 丢弃 各占多少）。这是一个新的诊断指标，不建议直接并入十维度评分——先作为独立展示，等有了足够标注数据再考虑要不要影响 Dataset Readiness Score。

### 2.6 开放问题：是否需要多标注者一致性

论文 §4.18 real AgentNexus validation 要求至少两名标注者、计算 Cohen's κ 或 Krippendorff's α。产品里要不要现在就支持"同一条记录多人标注 + 一致性计算"，是一个需要你决定的产品范围问题：
- 如果现在只是为了让专家把明显有问题的导入数据筛掉，单人标注 + 简单状态机就够，一致性分析可以留到后面；
- 如果这批标注数据以后要直接作为论文 §4.18 的标注数据源，那从一开始就应该支持多人标注同一条记录，并且记录标注者身份（现在的角色选择器 `useRole.ts` 只有一个"当前身份"，没有真正的多用户登录，这是之前记录过的假设 1 的老问题，这里会再次撞上）。

这一点我不替你决定，建议放到下一轮讨论。

## 3. 两个改动的关系与建议顺序

- 两者互不阻塞，可以并行排期。
- 如果只能先做一个，建议先做**修改二（Scenario/Case Context）**：改动集中在 `guide_service.py` 一个文件的 FSM 扩展 + `models.py` 加一个字段，改动面小、见效快，而且能立刻提升新采集数据的质量；修改一（标注流程）涉及新的数据表、新的页面/交互、以及一个需要你决策的产品范围问题（2.6），值得再讨论一轮细节之后再动手。

## 4. 待你确认的问题清单

1. A 组三问是否真的要设为"不可跳过"？还是也允许跳过但影响完整度分数？
2. B 组的四个问题要不要给预设 chip 选项（如上面 `constraints` 的例子），还是先做成纯自由文本，看实际数据再决定要不要结构化？
3. 标注流程要不要从一开始就支持多标注者 + 一致性计算（2.6）？
4. "大模型整合出来的工作流"（LLM-derived）除了走导入流程外，是否已经有具体的生成方式？如果还没有，这部分目前只能先按"和 public_extracted 走同一条标注流程"来设计，等生成方式明确后可能需要单独处理其溯源信息（比如记录是哪个 LLM、基于哪些原始记录聚合的）。
